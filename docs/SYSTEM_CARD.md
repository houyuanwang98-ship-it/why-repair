# Why-Repair 系统卡

版本：工程候选 v0.1  
更新：2026-09-10

## 系统用途

Why-Repair 是自然语言代数证明的研究与演示原型。它将证明拆为依赖节点，定位首个可操作问题，生成结构化错误证书，并在不改变原题的约束下提出局部补丁。确定性控制器管理版本、权限、预算、缓存、后代失效、回滚、重验和审计记录。

适合的用途包括：课堂演示、证明错误分析研究、结构化数据生成、受监督的证明诊断与修复实验。系统输出应被视为供人审查的候选意见。

## 不适合的用途

- 不应作为形式证明器或定理证明助理内核的替代品。
- 不应在无人复核时为高风险数学结论背书。
- 不应把“Schema 合法”“程序运行成功”或“补丁已应用”等同于数学正确。
- 不应对开放域、竞赛级或研究级数学能力作超出冻结数据的外推。
- 不应通过新增假设、弱化结论或改变定义域来制造修复成功。

## 输入与输出

输入包括题目、假设、自然语言证明、节点及其依赖。主要输出包括节点级 EvaluationRecord、首错 ErrorCertificate、PatchProposal、PatchReview、版本历史、失效记录与 RunManifest。证据不足时允许输出 `undetermined`；原命题为假或不改变问题便无法修复时允许输出 `mark_irreparable`。

## 核心安全机制

1. Evaluator 与 Repair Generator 权限分离，生成器不能批准自己的补丁。
2. 节点以 `(proof_id, node_id, version)` 绑定，阻止旧结果静默复用。
3. 修改节点后计算依赖后代闭包，清除旧缓存并按拓扑顺序重验。
4. 补丁接受不等于整篇证明成功；只有受影响路径完成重验后才能结束。
5. 对格式错误、版本过期、预算耗尽、模型异常和不确定判断执行失败闭合并保存记录。

## 已知性能证据

冻结 50 题工程集上的证明有效性分类准确率为 0.94，错误类型准确率为 0.92，首个问题定位整体准确率为 0.80，依赖边 F1 为 0.9167。26 个 Gold-invalid 证明中存在 1 个误接受，因此系统不具备零误判保证。完整口径和证据路径见 `docs/paper/ARTICLE_EVIDENCE_LEDGER_2026-09-10.md`。

M6/M7 中的 fixture、projection 与 Codex proxy 运行主要用于验证工程管线，不是正式跨模型性能证据。当前人工协议为 AI 预填后的单人复核，不是独立双盲标注。

## 主要风险

- 自然语言切分或依赖抽取错误可能改变后续判断。
- 定理适用条件、隐含定义域和量词范围可能被遗漏。
- 流畅但错误的模型输出可能诱导人工快速确认。
- 有界执行器无法覆盖一般自然语言数学语义。
- 数据量小、领域集中会造成性能估计偏乐观。
- 若外部 provider、模型版本或 Prompt 漂移，历史结果不可直接比较。

## 人工监督要求

人工至少应核查原题保持、首错位置、错误类型、补丁数学正确性和受影响后代。对 false accept、false repair、全局反例、改变假设/结论以及 `undetermined` 应优先复核。当前项目为减少劳力采用单一 Person B 人工角色与 AI 预填；发表时必须披露这一事实，不能声称独立标注一致性。

## 数据、隐私与许可

发布前应逐项确认数据来源、许可、去重、潜在训练污染和个人信息。密钥、个人身份信息、未授权题库及 provider 私有返回不得进入公开归档。仓库中的哈希用于检测字节变化，不构成身份认证或数学正确性证明。

## 复现边界

确定性测试和 fixture 可在固定代码与数据上回放。真实模型结果还需要冻结模型 snapshot、采样参数、Prompt、截断、预算、工具、价格表和原始调用记录。缺少这些条件时，只能声称管线可执行，不能声称外部结果已独立复现。

## 报告问题

发现数学误接受、错误修复、数据泄漏、版本/缓存污染或不可复现结果时，应保留样本 ID、输入摘要、配置身份、终态、原始输出和复现步骤，并停止传播受影响的聚合结论，直到证据台账完成修订。
