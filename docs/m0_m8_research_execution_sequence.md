# M0–M8 双人、Controller 与配套研究执行顺序

版本：`v0.1-draft`  
适用项目：依赖图驱动的双 Agent 自然语言数学证明审计与局部修复 Harness  
配套文档：[项目验证与强制验收计划](project_validation_and_acceptance_plan.md)

## 1. 文档目的

本文档回答以下执行问题：

- M0–M8 每个阶段由谁先开始、谁复核、谁最终验收。
- Person A、Person B、Evaluator、Repair Generator 与 Controller 的职责如何衔接。
- Schema、Prompt、定理库、Benchmark、实验、统计、文档和外部审查等配套事项应插入在哪一步。
- 哪些任务必须串行完成，哪些任务可以并行，哪些任务未通过验收门时不得进入下一阶段。
- 每次交接应提交什么输入、输出、证据和冻结版本。

本文档定义“做事顺序”；具体验证内容和强制验收标准以 `project_validation_and_acceptance_plan.md` 为准。

## 2. 角色与权限

### 2.1 Person A：Evaluator 与数学有效性

- 主责节点表示、依赖语义、局部证明义务、数学裁决和错误类型。
- 主责定理适用性、反例数学语义、人工标注指南和数学金标。
- 主责 Evaluator Prompt、Error Certificate 数学字段和补丁数学复核。
- 主责论文的问题定义、数学方法、错误分析和能力边界。
- 不得单方面修改共享 Schema、Controller 状态语义或主实验协议。

### 2.2 Person B：Repair、Controller 与实验工程

- 主责 PatchProposal、PatchReview、节点版本、失效传播、回滚和终止策略。
- 主责 Controller、模型适配、session、缓存、运行清单和审计日志。
- 主责 Repair Generator Prompt、评估运行器、基线、消融、统计和复现。
- 主责论文的系统实现、实验设置、成本分析和复现说明。
- 不得单方面改变数学裁决、错误类型或人工金标含义。

### 2.3 Evaluator Agent

- 接收题目、证明、合法上下文和已验证证据。
- 执行切分、分类、建图、局部义务验证、反例候选、诊断和补丁复核。
- 输出结构化数学判断，但必须经过 Controller 契约检查。
- 不修改证明，不接受自己未独立复核的补丁。

### 2.4 Repair Generator Agent

- 只接收被允许的局部上下文和 Error Certificate。
- 在修改预算内提交 PatchProposal 或 `mark_irreparable`。
- 不得接受自己的补丁，不得改变原题，不得重写无关分支。
- 输出经过 Controller 机械检查后，必须由 Evaluator 独立复核。

### 2.5 Controller

- 负责 Schema、DAG、状态、版本、缓存、重试、回滚和运行记录。
- 负责将任务发送给 Evaluator 或 Repair Generator，并校验响应格式。
- 负责节点改变后的后代撤销和拓扑重验证。
- 不判断定理是否成立，不把 JSON 合法等同于数学正确。
- 不作为第三个数学 Agent 参与自由推理。

### 2.6 其他配套角色

- **第二标注者：** 与首标者独立完成 Benchmark 标注。
- **第三方数学专家：** 裁决双人无法解决的数学分歧，复核全局反例和论文代表案例。
- **外部代码审查者：** 审查状态机、缓存、指标、数据泄漏和复现流程。
- **复现实验者：** 在干净环境执行发布命令并报告问题。
- **外部工具：** Python、SymPy、SAT/SMT、有限穷举和证明助手，仅在其明确能力范围内提供辅助证据。

## 3. 总体研究顺序

### 3.1 主线顺序

```text
M0 Person A 定义数学语义
→ M0 Person B 独立审查执行语义
→ M0 双人裁决与冻结

→ M1 Person A 起草数学 Schema
→ M1 Person B 起草执行 Schema 与 Controller 状态机
→ M1 Controller 骨架与契约测试
→ M1 双人交叉审查与冻结

→ M2 Person A 设计 Pilot Benchmark
→ M2 Person B 建立标注和数据工具
→ M2 Controller 做数据结构检查
→ M2 A/B 独立精标
→ M2 双人或第三方裁决并冻结数据

→ M3 Person A 实现 Evaluator 数学阶段
→ M3 Person B 实现模型适配和运行器
→ M3 Controller 编排分阶段调用
→ M3 A 做数学误差分析，B 做工程回归

→ M4 Person A 定义反例语义
→ M4 Person B 实现核验工具
→ M4 Controller 管理反例证书状态
→ M4 A/第三方复核高风险反例

→ M5 Person B 实现 Repair Generator 与 Patch 机制
→ M5 Controller 实现版本、失效、重验和回滚
→ M5 Person A 定义并执行补丁数学复核
→ M5 完整闭环端到端验收

→ M6 Person A 冻结研究问题、指标和公平性规则
→ M6 Person B 实现基线与消融
→ M6 Controller 冻结和运行实验配置
→ M6 A 审查数学可比性，B 审查工程完整性

→ M7 A/B 冻结正式 Benchmark 和主实验配置
→ M7 Person B 运行主实验
→ M7 Controller 保存并核对全部运行
→ M7 Person A 与第三方做盲态数学错误分析

→ M8 Person A 写数学方法、数据和错误分析
→ M8 Person B 写系统、实验、成本和复现
→ M8 Controller 生成表格、Manifest 和发布清单
→ M8 外部审查、独立复现、共同定稿和发布
```

### 3.2 不得颠倒的关键依赖

- M0 术语未冻结，不得冻结 M1 Schema。
- M1 Schema 和 Controller 骨架未通过，不得批量生成 M2 金标。
- M2 Pilot 金标未冻结，不得宣称 M3 模型性能有效。
- M3 Evaluator 分模块性能未测量，不得用端到端结果掩盖上游错误。
- M4 反例核验未完成，不得把模型候选反例作为正式证据。
- M5 后代撤销与独立复核未完成，不得进入修复主实验。
- M6 基线、公平性和指标未冻结，不得启动 M7 正式测试集运行。
- M7 主实验不完整或不可复现，不得在 M8 写出强量化结论。

### 3.3 可以并行的工作

- M1 中 A 可设计数学对象，B 可设计执行对象，但共享字段合并前必须交叉审查。
- M2 中 A 可准备题目与参考证明，B 可开发标注工具和数据检查器。
- M3 中 A 可开发 Evaluator Prompt，B 可开发 provider adapter、session 和运行日志。
- M4 中 A 可建立反例金标，B 可实现不同工具核验器。
- M5 中 B 可开发 Patch 状态机，A 可设计对抗性补丁和最小性标准。
- M8 中 A/B 可并行写作各自主责章节，但数字、术语和系统流程必须最后交叉统一。

## 4. 跨阶段固定工作循环

### 4.1 每项工作的标准顺序

```text
主责人提出规格
→ 非主责人审查跨边界影响
→ Controller/程序实现机械约束
→ 增加正反测试和人工案例
→ 双人验收
→ 冻结版本
→ 更新索引、变更记录和已知限制
```

### 4.2 每次交接必须包含

- 任务目标和明确非目标。
- 输入输出契约和版本。
- 实现位置、测试位置和运行命令。
- 正例、反例、边界例和失败例。
- 当前已知限制和未解决问题。
- 下一位负责人需要作出的具体判断。
- 是否已满足本阶段强制验收门。

### 4.3 每周固定节奏

- 周一：A/B 各确定一个可测量交付物，不以工作时长作为目标。
- 周中：异步更新实现、证据、失败案例和阻塞问题。
- 周五：只演示已完成产物、测试和实际失败，不以口头进度代替验收。
- 每两周：冻结一次 Schema、Prompt、数据或实验配置版本，用于可比回归。

### 4.4 全程维护的杂项

- README、PROJECT_INDEX、ROADMAP 和 CHANGELOG。
- milestone 验收记录、审查记录和裁决记录。
- Schema 版本、迁移说明和 fixture。
- Prompt 版本、修改理由和回归结果。
- 定理库来源、审计状态和覆盖率。
- 数据来源、许可、隐私、版本和划分。
- 测试、CI、运行清单、成本、失败日志和复现命令。

# 第一部分：各阶段详细研究顺序

## 5. M0：研究范围与术语契约

### 5.1 M0 Person A 首轮工作

1. 写明系统目标、研究边界和第一篇论文非目标。
2. 定义 ProofInstance、ProofNode、DependencyEdge 和 LocalObligation。
3. 定义数学裁决和错误类型。
4. 定义局部反例、全局反例、修复成功和最小修复。
5. 提出三个可量化研究问题和对应指标。
6. 准备覆盖术语边界的验收案例。
7. 在不查看 Person B 答案的情况下完成独立标注。

### 5.2 M0 Person B 第二轮工作

1. 独立阅读研究目标和非目标，检查是否可执行。
2. 独立标注相同验收案例。
3. 检查数学裁决和生命周期状态是否混用。
4. 检查每个术语是否能映射到字段、状态和测试。
5. 标记 Controller 能检查与不能检查的条件。
6. 起草版本、补丁和撤销的执行语义。
7. 列出模糊、循环或依赖模型信心的定义。

### 5.3 M0 Controller 与杂项工作

- 此阶段不实现完整 Controller，只定义权限边界和状态分类草案。
- 建立核心枚举清单和术语差异表。
- 保存 A/B 原始评审，不回写个人答案。
- 建立 M0 adjudication 文档和冻结记录。
- 更新 PROJECT_INDEX、ROADMAP 和 CHANGELOG。

### 5.4 M0 共同裁决顺序

1. Controller 或差异脚本列出所有标签分歧。
2. A/B 分别补充理由，避免先被对方说服后再补理由。
3. 对照定义逐项裁决。
4. 无法裁决的数学问题交第三专家。
5. 将最终规则同步到主契约。
6. 冻结 M0 版本，禁止静默修改。

### 5.5 M0 输出与退出条件

- 输出：范围契约、术语表、研究问题、指标、案例、双人评审和裁决记录。
- 退出：A/B 能用同一规则稳定判断案例，所有核心分歧已有书面结论。
- 下一阶段输入：冻结术语、状态边界和字段需求。

## 6. M1：共享 Schema 与 Controller 骨架

### 6.1 M1 Person A 数学对象顺序

1. 起草 `ProofInstance` 和 `ProofNode`。
2. 起草 `DependencyEdge` 和 `LocalObligation`。
3. 起草 `EvaluationRecord` 和合法数学裁决。
4. 起草 `ErrorCertificate` 的失败边、上下文和错误证据字段。
5. 起草 `CounterexampleCertificate` 的前提和目标检查字段。
6. 为每个对象编写至少一个正例和一个数学无效例。
7. 将对象交给 Person B 检查可执行性，不先写 Controller 特例绕过 Schema。

### 6.2 M1 Person B 执行对象顺序

1. 起草 `PatchProposal` 和 `PatchReview`。
2. 起草 `NodeVersion`、`LifecycleState` 和 `InvalidationRecord`。
3. 起草 `RunManifest`、`ModelInvocation`、`RetryRecord` 和 `CacheFingerprint`。
4. 起草完整状态转换表。
5. 标记每个状态转换所需的数学证据和机械条件。
6. 为过期版本、非法跳转、缺少复核和回滚失败编写 fixture。
7. 将执行对象交给 Person A 检查是否改变数学语义。

### 6.3 M1 Controller 实现顺序

1. 实现所有 Schema 的加载和验证。
2. 实现节点、边和 DAG 检查。
3. 实现数学裁决与生命周期状态的分离存储。
4. 实现节点版本和精确 Patch 目标检查。
5. 实现不可变事件日志和 RunManifest 骨架。
6. 实现状态转换守卫，不允许越级接受。
7. 实现两个不调用模型的虚拟修复会话回放。
8. 实现正反 fixture 的自动测试。

### 6.4 M1 杂项研究顺序

- 确定 JSON Schema 规范版本和兼容策略。
- 统一字段命名、枚举拼写和 null/缺失语义。
- 建立 schema migration 模板。
- 建立数据样例目录和测试 fixture 目录。
- 建立 milestone 验收记录模板。
- 更新开发文档、仓库索引和变更记录。

### 6.5 M1 交叉审查与退出

1. A 检查 Controller 没有把格式合法当成数学正确。
2. B 检查数学对象没有依赖不可记录的隐含状态。
3. 双人检查 ErrorCertificate 能被 Repair Generator 消费。
4. 运行全部 Schema、图和状态机测试。
5. 冻结 Schema v0.1 和状态转换表。

## 7. M2：Pilot Benchmark 与人工精标

### 7.1 M2 Person A 数据设计顺序

1. 确定 Pilot 错误类型和难度分布。
2. 收集正确题目、参考证明和可信来源。
3. 审查原题完整性和参考证明正确性。
4. 创建正确证明、真实缺口、错误推理、局部假命题、定理误用和计算错误样本。
5. 对人工注入错误保存修改前后版本和注入说明。
6. 起草节点、依赖、裁决、反例和修复标注指南。
7. 准备资格测试和校准案例。

### 7.2 M2 Person B 数据工具顺序

1. 实现数据 Schema 和命令行校验器。
2. 实现节点 span、节点覆盖、edge 和 DAG 检查。
3. 实现双人标注差异和一致性报告。
4. 实现去重、近重复和划分泄漏初筛。
5. 实现数据版本、hash 和来源记录。
6. 实现 Gold 生成流程，禁止覆盖原始标注。
7. 实现数据审计报告和失败退出码。

### 7.3 M2 Controller 插入顺序

1. 接收原始样本并做结构校验。
2. 生成 A/B 两份相互隔离的标注任务。
3. 锁定标注期间不可见的信息，包括对方答案和模型预测。
4. 收集原始标注，生成字段级差异。
5. 保存共同裁决和第三方裁决。
6. 生成不可变 Gold 版本和数据 Manifest。
7. 冻结 train/dev/test 划分。

### 7.4 M2 人工精标顺序

1. A 与 B 分别完成资格测试。
2. 两人独立标注全部 Pilot 样本。
3. Controller 计算一致性，不直接决定数学标签。
4. 双方先分别写分歧理由。
5. 共同裁决；无法解决时交第三专家。
6. 根据真实分歧一次性修订指南。
7. 使用修订后指南复查受影响样本。

### 7.5 M2 杂项研究顺序

- 检查数据许可、教材版权和学生隐私。
- 建立数据卡和来源索引。
- 统计错误类型、证明长度、节点数和图结构分布。
- 检查同源题、变量替换和模板近重复。
- 检查定理库和 Prompt 示例是否泄漏测试答案。
- 更新 annotation guideline 和 benchmark README。

### 7.6 M2 输出与退出

- 输出：Pilot 数据、A/B 原始标注、裁决、Gold、数据卡和一致性报告。
- 退出：每个样本可追踪到来源、参考证明、标注和裁决。
- 下一阶段输入：冻结的 Pilot Gold，可用于 M3 分模块评价。

## 8. M3：Evaluator v1

### 8.1 M3 Person A 实现顺序

1. 冻结每个 Evaluator 阶段的输入输出契约。
2. 实现或优化节点切分 Prompt。
3. 实现节点分类和 self-contained claim Prompt。
4. 实现 ambient context 提取与 abstention 规则。
5. 实现全局 Graph Builder 和直接依赖解释。
6. 实现局部证明义务裁决。
7. 实现第一错误定位和结构化 diagnosis。
8. 将 diagnosis 映射为 ErrorCertificate。
9. 使用上游 Gold 隔离评测各模块。
10. 对错误接受案例逐项做数学误差分析。

### 8.2 M3 Person B 工程顺序

1. 实现模型 provider adapter 和统一调用接口。
2. 实现 Prompt 注册、版本和 hash。
3. 实现请求重试、超时、失败和成本记录。
4. 实现分模块 runner 和批量运行器。
5. 实现 session、response ledger 和断点恢复。
6. 实现依赖前沿调度和独立节点批处理。
7. 实现节点级缓存和 changed-only 输出。
8. 为模型格式错误、矛盾响应和无进展建立回归测试。

### 8.3 M3 Controller 编排顺序

```text
输入校验
→ segmentation 调用与校验
→ classification/self-contained claim 调用与校验
→ ambient 调用与证据校验
→ graph 调用与完整 DAG 校验
→ dependency frontier 计算
→ local obligation 构造
→ retrieval
→ proof/calculation adjudication
→ diagnosis
→ ErrorCertificate 校验
→ 保存结果、缓存和 RunManifest
```

### 8.4 M3 配套研究顺序

- Person A 维护错误案例集和 Prompt 修改理由。
- Person B 维护模型版本、成本和失败率报告。
- 定理库维护者审计 deterministic-safe 规则。
- 指标代码先用手算 fixture 验证，再运行 Pilot。
- 开发集用于 Prompt 调整，测试集保持封闭。
- 更新 skill 文档、development guide 和 changelog。

### 8.5 M3 交叉审查与退出

1. A 检查局部上下文没有后续或无关信息泄漏。
2. B 检查各阶段失败不会静默继续。
3. A 审查所有 false acceptance。
4. B 审查 session、缓存和重放一致性。
5. 分别报告模块指标和端到端指标后进入 M4。

## 9. M4：反例生成与独立核验

### 9.1 M4 Person A 数学顺序

1. 定义 CandidateCounterexample 和 CounterexampleCertificate。
2. 定义全局假设、局部前提和目标否定检查项。
3. 定义 local/global scope 和对应系统动作。
4. 为每种错误类型建立正反反例案例。
5. 明确哪些问题可程序完备核验，哪些只能辅助检查。
6. 复核程序编码与自然语言命题的一致性。
7. 对全部全局反例进行人工复核。

### 9.2 M4 Person B 工具顺序

1. 实现候选反例统一接口。
2. 实现精确数值和代数代入核验。
3. 接入 SymPy 或其他符号工具。
4. 对适合领域实现有限穷举或 SAT/SMT 核验。
5. 保存工具输入、输出、版本、参数和超时状态。
6. 对部分解析、浮点误差、`unknown` 和工具失败采用 fail-closed。
7. 编写无效反例和错误编码回归测试。

### 9.3 M4 Controller 插入顺序

```text
Evaluator 提交候选反例
→ Controller 校验目标节点与版本
→ 标记 pending_verification
→ 调用适用核验器
→ 汇总全部前提检查
→ 检查目标否定
→ 确定 local/global 证书状态
→ Person A/第二专家人工复核高风险结果
→ 写入最终裁决或拒绝候选
```

### 9.4 M4 杂项研究顺序

- 建立反例工具覆盖表和不支持表达式清单。
- 将无效反例按失败原因分类，用于论文分析。
- 统计发现率、有效率、假反例率和核验成本。
- 为外部工具固定版本和环境说明。
- 对全局反例保存适合论文展示的人工可读证书。

### 9.5 M4 输出与退出

- 输出：反例协议、核验器、证书、测试集和统计报告。
- 退出：没有未经核验候选被当作数学证据；全局反例通过双重验证。
- 下一阶段输入：可由 ErrorCertificate 引用的正式反例证书。

## 10. M5：Repair Generator 与完整修复闭环

### 10.1 M5 Person B 先行工作

1. 冻结 Repair Generator 输入 Schema。
2. 冻结 PatchProposal、PatchReview 和修改预算。
3. 实现 `insert_before`、`replace`、`delete` 和 `mark_irreparable`。
4. 实现 Repair Generator Prompt 和模型调用适配。
5. 实现补丁目标版本、操作范围和依赖引用检查。
6. 实现等价补丁检测、最大修复轮数和停止原因。
7. 实现补丁应用与回滚事务。

### 10.2 M5 Controller 核心顺序

```text
Evaluator 生成 ErrorCertificate
→ Controller 校验证书并冻结目标版本
→ Controller 生成允许的局部修复上下文
→ Repair Generator 提交 PatchProposal
→ Controller 检查 Schema、版本、预算、引用与 DAG
→ Evaluator 独立复核新增/替换节点
→ Controller 记录 PatchReview
→ 若接受，创建新节点版本并应用 Patch
→ 计算全部受影响后代闭包
→ 将旧裁决标记 stale，清除相关缓存
→ 按拓扑序重新交给 Evaluator
→ 检查最终目标路径状态
→ 接受、拒绝、重试、回滚或终止
```

### 10.3 M5 Person A 数学复核顺序

1. 定义补丁允许使用的数学证据。
2. 定义修复成功和操作意义上的最小性。
3. 设计正确补丁、似是而非补丁、隐藏假设补丁和目标偷换补丁。
4. 为 PatchReview 设计对抗式复核 Prompt。
5. 对新增节点逐项验证。
6. 检查原失败边是否真正解决。
7. 检查原题、假设、定义域和无关分支未改变。
8. 检查后代重验结果和新错误引入。

### 10.4 M5 杂项研究顺序

- 建立 Patch 等价与文本差异规则。
- 建立 repair budget 的不同设置和消融配置。
- 建立不可修复、需要改变题目和全局反例停止案例。
- 维护完整版本链和审计可视化。
- 统计修复轮数、补丁大小、成本和失败原因。
- 更新用户输出格式，使“修复”和“改变问题建议”明显分开。

### 10.5 M5 端到端验收顺序

1. 先用纯 fixture、不调用模型测试状态机。
2. 再用人工指定 ErrorCertificate 和 Patch 测试闭环。
3. 再接入 Repair Generator 跑 Pilot。
4. A 审查所有成功补丁和 false repair。
5. B 审查失效、缓存、回滚和循环终止。
6. 所有强制门通过后才允许进入 M6。

## 11. M6：基线、消融与实验协议冻结

### 11.1 M6 Person A 先冻结科学问题

1. 冻结 RQ1–RQ3 和主要假设。
2. 冻结第一错误、错误接受、反例有效和修复成功定义。
3. 冻结主要指标、次要指标和分层分析。
4. 定义各基线应获得的信息和工具权限。
5. 审查 token 预算和调用次数是否具有数学可比性。
6. 冻结错误案例分析模板。
7. 在看正式测试结果前签署实验协议。

### 11.2 M6 Person B 实验实现顺序

1. 实现整篇证明直接判断基线。
2. 实现单 Agent 自我反思基线。
3. 实现普通 Generator–Critic 基线。
4. 实现无图双 Agent。
5. 实现无结构化 Error Certificate。
6. 实现无反例协议。
7. 实现无后代撤销。
8. 实现单轮修复和完整系统。
9. 配置同模型双角色和异模型双角色。
10. 为每个配置生成唯一实验 ID 和 Manifest。

### 11.3 M6 Controller 运行顺序

1. 冻结数据、代码、定理库、Prompt、模型和指标 hash。
2. 检查所有方法的样本集合和失败处理一致。
3. 运行开发集 smoke test。
4. 运行 Pilot 基线和消融。
5. 保存成功、失败、超时、重试和成本。
6. 生成聚合结果和字段级完整性报告。
7. 禁止缓存跨方法或跨配置污染。
8. 保存冻结后的主实验配置候选。

### 11.4 M6 杂项研究顺序

- 用手算 fixture 检查指标实现。
- 设计 bootstrap、配对比较和多重比较方案。
- 记录模型版本漂移风险。
- 计算统计功效或合理样本量范围。
- 建立图表和表格自动生成脚本。
- 对预算不公平或实现异常的基线重新审查，而不是直接纳入论文。

### 11.5 M6 交叉审查与退出

1. A 检查所有基线的数学信息是否公平。
2. B 检查所有消融只改变目标组件。
3. Controller 检查失败运行没有被删除。
4. 双人确认主实验协议和配置。
5. 冻结 M7 输入，不再根据测试结果调 Prompt。

## 12. M7：正式 Benchmark 与主实验

### 12.1 M7 数据冻结顺序

1. A 扩展并审查 200–500 个高质量样本。
2. B 运行去重、泄漏、Schema 和分布检查。
3. A/B 对新增样本独立标注或复核。
4. 第三专家处理全局反例和重大争议。
5. Controller 生成最终 Gold 和数据 Manifest。
6. 冻结测试集并限制访问。

### 12.2 M7 Person B 主实验顺序

1. 冻结代码提交和依赖环境。
2. 对所有配置运行小规模 smoke test。
3. 执行全部基线。
4. 执行全部关键消融。
5. 执行完整系统同模型组合。
6. 执行至少一组异模型组合。
7. 执行预定 seed 或重复采样。
8. 生成原始结果、成本和失败日志。

### 12.3 M7 Controller 运行治理顺序

- 为每次运行验证 Manifest 和输入 hash。
- 确保每种方法覆盖相同样本或记录缺失原因。
- 不因失败、超时或低分删除运行。
- 校验输出与实验配置对应。
- 计算配对指标、置信区间和分层结果。
- 在独立目录抽样重放完整推理链。
- 生成主实验完整性报告。

### 12.4 M7 Person A 与外部专家顺序

1. 在尽可能不知道方法名称的条件下审查错误案例。
2. 复核所有错误接受、错误全局反例和错误修复。
3. 分析 gap/invalid、local/global 和 blocked/error 的混淆。
4. 第三专家复核论文候选案例和异常结果。
5. 将失败归因于表示、图、检索、验证、反例、修复或 Controller。
6. 不根据失败案例修改测试金标；如有真实金标错误，执行公开勘误和全量重跑。

### 12.5 M7 杂项研究顺序

- 统计 token、调用数、延迟和总成本。
- 进行多 seed 稳定性和模型版本敏感性分析。
- 生成错误类型、难度、长度和图结构分层表。
- 保存所有失败运行和失败原因。
- 撰写初步结果说明，但不在复现前形成最终主张。

### 12.6 M7 输出与退出

- 输出：完整原始结果、Manifest、聚合表、置信区间、成本和错误分析。
- 退出：核心结果可回放，失败运行完整，主要结论在预定分析下成立或被否定。
- 下一阶段输入：冻结的论文数字和经过审查的代表案例。

## 13. M8：论文、发布与复现

### 13.1 M8 Person A 写作顺序

1. 写问题定义、研究边界和相关任务区别。
2. 写依赖图、局部义务、Evaluator 和 Error Certificate。

7. 审核论文所有数学公式、定理引用和案例。

### 13.2 M8 Person B 写作顺序

1. 写 Controller、状态机、版本、缓存和撤销机制。
2. 写 Repair Generator、Patch 和重试终止策略。
3. 写模型、Prompt、工具、基线和消融配置。
4. 写指标、统计、成本和复现设置。
5. 准备代码、数据、系统卡和运行说明。
6. 审核所有实现描述与真实代码一致。
7. 准备发布版本和归档标识。

### 13.3 M8 Controller 与自动化顺序

1. 从原始结果重新生成所有表格和图表。
2. 校验论文数字、分母、样本量和置信区间。
3. 生成代码、数据、Prompt、模型和定理库版本表。
4. 生成复现命令、文件 hash 和发布清单。
5. 执行完整测试、数据审计和隐私扫描。
6. 在干净环境执行确定性复现和小规模模型实验。
7. 将最终发布结果与论文提交版本绑定。

### 13.4 M8 外部审查顺序

1. 第三方数学专家复核核心案例和数学主张。

5. 重大修改触发受影响实验重跑和论文数字更新。

### 13.5 M8 最终发布顺序

```text
→ 系统与实验描述冻结

→ 外部审查

→ 发布代码、数据、文档和论文
```

# 第二部分：跨阶段配套研究顺序

## 14. Schema 研究顺序

### 14.1 初始设计

- M0 冻结概念，M1 才正式创建共享 Schema。
- A 先定义数学含义，B 再定义版本和执行字段。
- Controller 实现严格验证和负向 fixture。
- 双人冻结版本，任何修改都必须有迁移说明。

### 14.2 后续变更

- M2 根据真实标注问题发现缺陷。
- M3–M5 只有无法表达必要证据时才扩展字段。
- 变更先在新版本试验，再迁移数据、测试和 Prompt。
- 主实验冻结后禁止破坏性变更。

## 15. Prompt 研究顺序

### 15.1 开发顺序

- A 主责 Evaluator Prompt，B 主责 Repair Generator 和运行包装 Prompt。
- 每个职责使用独立 Prompt 和 Schema。
- 先在合成 fixture 上测试格式，再在开发集测试数学性能。
- 每次修改记录版本、理由、预期影响和回归结果。

### 15.2 冻结顺序

- M3 冻结 Evaluator v1 Prompt。
- M5 冻结 Repair Generator v1 Prompt。
- M6 在主实验协议中冻结全部 Prompt hash。
- M7 不允许根据测试结果调 Prompt。

## 16. 定理库研究顺序

### 16.1 构建顺序

- A 定义条目数学字段和 deterministic-safe 标准。
- 数据抽取后先做来源、陈述和前提审计。
- B 实现规范化、索引、检索和版本 hash。
- 高风险安全规则由双人审核后才能启用确定性闭合。

### 16.2 评估顺序

- 建立 query–rule 金标。
- 先测 Recall@K，再测适用性判断。
- 分开评估 justification、diagnosis 和 repair retrieval。
- 主实验冻结 theorem-bank 版本，避免测试期扩库。

## 17. 人工标注研究顺序

### 17.1 标注准备

- 先冻结术语，再写指南和资格测试。
- 标注员通过校准题后才能标正式数据。
- 任务分配应隔离对方答案和模型预测。
- 每个字段允许 `uncertain` 或转交专家。

### 17.2 裁决与维护

- Controller 生成差异，人工解释和裁决。
- 指南修改后复查所有受影响样本。
- 原始标注和裁决分开保存。
- 测试集金标冻结后只允许公开勘误。

## 18. 测试与 CI 研究顺序

### 18.1 测试层级

- 单元测试：解析、图、状态、缓存、指标和工具适配。
- 契约测试：所有 Agent 输出和共享 Schema。
- 回归测试：每个历史缺陷对应至少一个案例。
- 端到端测试：无模型 fixture、受控模型响应和真实模型运行。

### 18.2 CI 顺序

- 每次提交先运行快速确定性测试。
- Schema、数据或定理库变化运行对应审计。
- Prompt 或模型适配变化运行固定开发回归集。
- release candidate 运行完整测试、数据检查和复现 smoke test。

## 19. 指标与统计研究顺序

### 19.1 指标开发

- A 定义数学意义，B 实现计算代码。
- 使用手算小样本交叉验证分子、分母和弃权处理。
- 分开 node、proof 和 first-error 层级。
- 先冻结主要指标，再查看正式测试结果。

### 19.2 统计分析

- 使用配对方法比较同一样本上的系统。
- 预先定义 bootstrap 单位和重复次数。
- 报告效应量、置信区间和多次运行方差。
- 多重比较采用预定修正，不只展示显著结果。

## 20. 文档、索引与变更管理顺序

### 20.1 每阶段更新

- 主规格写入对应 docs 或 milestone 文档。
- PROJECT_INDEX 只记录状态和真实成果链接。
- ROADMAP 更新阶段状态，不复制设计细节。
- CHANGELOG 记录新增、变更、修复和破坏性迁移。

### 20.2 变更审批

- 数学标签变化由 A 主提、B 审查执行影响。
- Controller 或 Patch 语义变化由 B 主提、A 审查数学影响。
- 共享 Schema 和主实验协议必须双人批准。
- 金标变化必须有裁决记录。

## 21. 外部审查与开放研究顺序

### 21.1 第三方数学审查

- M2 开始抽查争议金标。
- M4 复核全局反例。
- M5 复核高风险成功修复。
- M7–M8 复核论文代表案例和核心数学主张。

### 21.2 外部代码与复现

- M5 后审查状态机和后代撤销。
- M6 后审查指标、公平性和数据泄漏。
- M7 后执行独立环境复现。
- M8 发布前复查许可证、隐私和完整发布包。

## 22. 算力与模型使用顺序

### 22.1 第一阶段

- 使用强 API 模型验证任务契约和系统方法。
- 将资源优先投入高质量标注、协议、Controller 和评估。
- 不在 Benchmark 和指标未稳定前微调模型。

### 22.2 第二阶段

- 在 M6–M7 使用开源模型做可复现规模实验。
- 比较同模型和异模型双角色。
- 固定模型版本、推理参数和硬件环境。
- 只有确认存在稳定能力瓶颈后再考虑微调。

## 23. 风险处理顺序

### 23.1 数学风险

- 先保留 `undetermined`，再请求独立核验。
- 发现全局反例时停止原题修复并升级人工复核。
- 发现标签定义缺陷时暂停受影响实验，版本化修订。
- 发现测试金标错误时公开勘误并全量重跑。

### 23.2 工程风险

- 发现 stale 泄漏、缓存污染或状态越权时停止主实验。
- 修复缺陷、增加回归测试并重新验证受影响结果。
- API 或工具失败保留原始日志，不人工补写成功结果。
- 无法恢复的运行标记失败，不从统计中静默删除。

### 23.3 科学性风险

- 发现基线预算不公平时先重设实验，不解释结果。
- 发现 Prompt 对测试集调优时作废受影响运行。
- 发现完整系统提升只来自更多调用时修改论文主张。
- 结果不稳定时报告方差和边界，不只选择最好运行。

# 第三部分：阶段交接与启动门

## 24. M0 → M1 交接

- 必须提供冻结术语、研究问题、状态边界和裁决记录。
- M1 不得重新解释 M0 标签而不创建新版本。
- A 提交数学字段需求，B 提交执行字段需求。
- 未解决核心术语分歧时不得启动共享 Schema 冻结。

## 25. M1 → M2 交接

- 必须提供通过测试的 Schema、状态机、图校验和 fixture。
- Benchmark 标注格式必须使用冻结 Schema。
- 数据工具不得自创标签或改变 null/unknown 语义。
- 无法完整表示金标时先修 Schema，再继续批量标注。

## 26. M2 → M3 交接

- 必须提供冻结 Pilot Gold、数据卡、划分和一致性报告。
- Evaluator 开发只使用训练和开发部分。
- 测试部分对 Prompt 开发保持封闭。
- 模块指标必须能够用 Gold 上游输入独立计算。

## 27. M3 → M4 交接

- 必须提供稳定的失败节点、合法上下文和 ErrorCertificate 雏形。
- 反例模块不得接收未固定解释的目标而直接搜索。
- Evaluator 的无反例输出不能预先决定数学裁决。
- M3 的错误接受案例优先进入 M4 压力测试。

## 28. M4 → M5 交接

- 必须提供正式 CounterexampleCertificate 和核验状态。
- ErrorCertificate 可引用反例，但不能引用未经核验候选。
- 全局反例案例进入 Repair Generator 停止测试。
- 局部反例案例进入 replace/insert Patch 测试。

## 29. M5 → M6 交接

- 必须提供完整闭环、独立 PatchReview 和后代撤销测试。
- 成功修复必须满足最终路径状态检查。
- 修复失败、循环、回滚和改变题目均有明确记录。
- 闭环未通过时不得将完整系统作为论文方法运行正式消融。

## 30. M6 → M7 交接

- 必须冻结研究问题、指标、基线、消融、预算和失败处理。
- 必须提供所有配置的 smoke test 和公平性审查。
- 测试集运行前冻结代码、Prompt、模型和定理库 hash。
- 任何未解决的指标实现错误都会阻止主实验。

## 31. M7 → M8 交接

- 必须提供完整原始结果、Manifest、置信区间、成本和错误分析。
- 论文数字只能来自冻结的结果生成流程。
- 代表案例必须通过数学复核并对应真实运行轨迹。
- 无法复现或不稳定的结论只能弱化表述或列为限制。

## 33. 建议的最终执行原则

- 数学定义由 Person A 先提出，执行约束由 Person B 接续，Controller 最后机械化。
- 系统机制由 Person B 先实现，数学影响由 Person A 复核，Controller 用测试固定行为。
- 数据由 Person A 设计，工具由 Person B 实现，A/B 独立精标，Controller 管理差异和版本。
- 实验由 Person A 先冻结科学问题，Person B 实现和运行，Controller 留痕，A 与外部专家解释结果。
- 所有重要修改都遵循“规格 → 交叉审查 → 实现 → 测试 → 验收 → 冻结 → 索引”的顺序。
- 任一阶段出现数学证据不足、状态不一致、数据泄漏或无法复现时，应停止向后推进，而不是用更多 Agent 调用掩盖问题。
