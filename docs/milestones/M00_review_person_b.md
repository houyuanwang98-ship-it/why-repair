## 1. 独立案例标注

### 案例 A：显式消去

- 节点类型：`conclusion`。
- 直接依赖：无前序证明节点；使用全局假设 `a != 0`、`ax = ay` 和显式引用的消去律。
- 最终裁决：`accepted`。
- 错误类型：不适用。
- 理由：消去律是明确、适用的单个原子规则，不需要新增中间数学命题。规则引用应进入证据字段，而不是产生一个虚构的依赖节点。

### 案例 B：缺失非零条件

- 节点类型：`conclusion`。
- 直接依赖：无前序证明节点；仅有全局假设 `ax = ay`。
- 最终裁决：`counterexample_found`，范围为 `global_theorem`（本案例的唯一待证结论也是全局结论）。
- 错误类型：`false_theorem`；根因还可记录为缺少必要前提 `missing_assumption`。
- 反例核验：在实数中取 `a = 0, x = 1, y = 2`，有 `ax = ay = 0`，但 `x != y`。
- 备注：题面中的 `theore_misuse` 是非正式拼写；即使按“试图使用消去律”解释，正式枚举也应写作 `theorem_misuse`。在没有完整反例证书时，可暂记 `unsupported / missing_assumption`。

### 案例 C：省略桥接步骤

- 节点类型：`conclusion`。
- 直接依赖：无前序证明节点；使用全局假设 `a != 0`、`ax = ay`。
- 最终裁决：`accepted`。
- 错误类型：不适用。
- 理由：由非零因子消去是一个标准原子规则的直接应用。没有写出规则名称不等于省略了中间数学命题。只有复核时确实必须补入至少一个中间命题（而非仅补规则名称或解释）才标为 `accepted_with_gap`。

### 案例 D：局部命题错误，但原定理仍可修复

节点 1：

- 节点类型：`definition`（为偶数假设引入见证元 `k`）。
- 直接依赖：无前序证明节点；使用全局假设“`n` 为偶数”。
- 最终裁决：`accepted`。
- 错误类型：不适用。

节点 2：

- 节点类型：`calculation`。
- 直接依赖：节点 1。
- 最终裁决：`counterexample_found`，范围为 `local_claim`。
- 错误类型：`algebraic_invalidity`，并标明该节点构成 `false_local_claim`。
- 反例核验：取 `k = 1`，则节点 1 给出 `n = 2`，故 `n^2 = 4`，而 `2k^2 = 2`。
- 备注：题面中的 `algebraic_mismatch` 不是契约内正式枚举。

节点 3：

- 节点类型：`conclusion`。
- 直接依赖：节点 2（按原证明路线）。
- 当前 Controller 状态：`blocked_by_invalid_dependency`。
- 独立错误类型：不适用；在无效父节点被替换前不对该节点作新的数学错误诊断。

局部修复：将节点 2 替换为 `n^2 = (2k)^2 = 4k^2 = 2(2k^2)`。这保持原定理与假设不变；替换后节点 3 必须基于新版本重新验证。

### 案例 E：群中错误交换

- 节点类型：`conclusion`。
- 直接依赖：无前序证明节点；使用全局群假设。
- 最终裁决：若已核验具体非阿贝尔群反例，则为 `counterexample_found`，范围为 `global_theorem`；在反例证书完成前为 `unsupported`。
- 错误类型：有证书时为 `false_theorem`；无证书时为 `missing_assumption`（缺少交换群条件）。
- 反例示例：在对称群 `S_3` 中取 `a = (12)`、`b = (23)`，则 `ab != ba`。
- 备注：仅当原文确实给出了交换性节点而建图时漏掉它，才应诊断为 `dependency_error`。

### 案例 F：下游无效

节点 1：

- 节点类型：`claim`（无推导而引入的局部断言）。
- 直接依赖：无前序证明节点；背景为 `x` 是实数。
- 最终裁决：`counterexample_found`，范围为 `local_claim`。
- 错误类型：`false_local_claim`。
- 反例核验：取任意实数（例如 `x = 0`），均不能满足 `x^2 = -1`；更直接地，实数平方非负。

节点 2：

- 节点类型：`calculation`。
- 直接依赖：节点 1。
- Controller 状态：`blocked_by_invalid_dependency`。
- 数学说明：条件命题 `x^2 = -1 => x^4 = 1` 的平方运算本身有效，但当前证明不能把已拒绝的节点 1 当作已验证前提。`blocked_by_invalid_dependency` 是生命周期状态，不是节点 2 的独立错误类型。

### 案例 G：定义还是推理

- 节点类型：`definition`。
- 直接依赖：无。
- 最终裁决：在常规实值多项式语境或定义域、值域已由 ambient context 固定时为 `accepted`；若这些信息对良定义性有实质影响且未提供，则为 `undetermined`。
- 错误类型：通常不适用。
- 理由：定义不需要从前提推导，但仍需满足类型与良定义性约束。系统不能凭模型默认补出会改变裁决的定义域或值域。

### 案例 H：定理适用条件

- 节点类型：`conclusion`，证据字段记录极值定理引用。
- 直接依赖：无前序证明节点；使用全局假设“`f` 在 `(0,1)` 上可微”。
- 最终裁决：若完成反例证书则为 `counterexample_found`，范围为 `global_theorem`；否则为 `unsupported`。
- 错误类型：主要为 `theorem_misuse`；也应记录缺少闭区间上连续性/紧致定义域这一适用条件。若使用已核验反例（例如 `f(x)=x` 在 `(0,1)` 上可微但不取得最大值），可进一步标记 `false_theorem`。
- 理由：极值定理的适用条件不满足；这不是语义歧义，也不能因未找到反例转为接受。

### 案例 I：切分错误

- 表示裁决：两段切分无效，错误类型为 `segmentation_error`。
- 节点 1：`如果 a = 0，` 是语法残片，不能获得数学 `node_type`、直接依赖或数学裁决。
- 节点 2：脱离条件前件后改变了真实局部义务，因此不能独立裁决为原命题。
- 修正表示：合并成单个完整节点 `如果 a = 0，那么对任意 x,y 都有 ax = ay。`；合并后主要类型为 `conclusion`，直接依赖为空，并可由实数乘法的零元性质裁决为 `accepted`。

### 案例 J：信息不足的定理引用

- 节点类型：`conclusion`，证据字段记录“标准延拓引理”的未解析引用。
- 直接依赖：无法从给定文本确定；不得虚构依赖。
- 最终裁决：`undetermined`。
- 错误类型：当前不适用；只有查明具体引理后确认缺少适用条件，才诊断 `missing_assumption` 或 `theorem_misuse`。
- 理由：缺少引理陈述、映射类型、定义域和值域，现有证据既不足以接受，也不足以构造针对确定命题的反例。名称相似度不能作为数学证据。

## 2. 审阅清单

### 2.1 是否存在循环定义或仅依赖模型置信度的定义？

核心术语没有明显循环定义，也没有把模型置信度直接定义为数学正确性。但仍有两个执行风险：

1. “已核验背景事实”和“明确且适用的规则”必须具有可追踪来源或核验记录，否则实现可能退化为模型自报可信。
2. “最小且连续的中间推理链”的最小性只应相对于 harness 实际考虑并接受的候选集合，不应暗示全局最短证明。

### 2.2 `accepted` 与 `accepted_with_gap` 能否稳定区分？

基本可区分，但必须固定操作判据：一个已核验原子规则、定义展开或原子计算可以直接得到目标，且无需新增中间数学命题时为 `accepted`；必须新增至少一个可独立真假判断的中间数学命题时为 `accepted_with_gap`。不能按句子长度、节点数量、解释文字多少或模型主观难度划分。案例 A、C 均为 `accepted`。

### 2.3 `unsupported`、`ambiguous` 与 `undetermined` 能否稳定区分？

可以，前提是按证据状态而非置信度执行：

- `unsupported`：目标解释已固定，合法上下文也已固定，并已有证据表明当前推理缺少支持或规则不适用。
- `ambiguous`：存在至少两个实质合理解释，且解释选择会改变裁决；必须保存解释分支。
- `undetermined`：目标或所需外部事实尚缺足够可核验证据，当前既不能接受也不能反驳；案例 J 属于此类。

### 2.4 局部反例与全局反例的范围是否明确？

概念上明确，但证书必须显式携带 `scope`，并分别绑定 `target_node_id/version` 与 `proof_id/theorem_version`。局部节点为假只推出 `local_claim`，不能自动推出原定理为假；只有满足原题全部假设并否定最终结论时才能使用 `global_theorem` / `false_theorem`。

### 2.5 修复成功条件是否可检查或已明确分配？

大部分可执行，但第 1、2 项含数学判断，必须由独立 Evaluator 给出，Controller 只能核验记录和状态转换：

- 条件 1、2：Evaluator 检查，Controller 验证评审记录绑定到精确节点版本且裁决属于预先允许集合。
- 条件 3：Controller 根据旧、新依赖闭包计算受影响后代，并检查全部后代存在新版本复核记录。
- 条件 4：Controller 扫描目标依赖路径的当前状态，不得包含拒绝、`stale`、阻塞或未解决节点。
- 条件 5：Controller 对定理和全局假设使用规范化内容哈希/版本指纹进行不变性检查；语义等价但文本变化不能由 Controller 自行断言。
- “最小修复”：Evaluator 对候选删减后的数学有效性作判断，Controller 负责枚举删除检查、记录结果和确保无漏项。

### 2.6 Controller 生命周期状态是否与数学裁决分离？

概念上已分离，但数据实现应使用两个字段或两个独立枚举，例如 `mathematical_verdict` 与 `lifecycle_state`。`stale`、`blocked_by_invalid_dependency`、待复核、重试耗尽等不得写入数学裁决枚举；Controller 也不得把 JSON Schema 通过当成数学接受。

### 2.7 哪些案例仍可能产生分歧，根本原因是什么？

- 案例 C：分歧来自“未写规则名称”是否算桥接缺口。应以是否新增中间数学命题判定，而非文本显式程度。
- 案例 D：分歧来自把根因错误类型（`algebraic_invalidity`）与反例范围标签（`false_local_claim`）压入同一单值字段。Schema 应明确主错误类型及补充诊断的关系。
- 案例 E、H：分歧来自“已知缺少前提”与“已经完成反例证书”处于不同证据阶段。最终裁决必须随证书状态变化，并保留诊断轨迹。
- 案例 F：分歧来自混合数学裁决和 Controller 生命周期状态。无效父节点应阻塞下游，而不是自动给下游创造新的数学错误。
- 案例 G：分歧来自 ambient context 未固定，尤其是定义域和值域。
- 案例 J：分歧来自把未知外部定理误写成已知错误；在具体陈述被解析前应保持 `undetermined`。

## 3. 成员 B 的执行语义结论

M0 可以进入共同裁决，但冻结前建议确保以下约束在后续 Schema 中可表示：

1. 数学裁决、诊断错误、反例范围和生命周期状态彼此分离。
2. 每份裁决、反例证书和补丁评审都绑定精确的 `(proof_id, node_id, version)` 与依赖指纹。
3. 节点版本变化后，Controller 确定性地使依赖闭包中的旧裁决失效，并按拓扑顺序重验。
4. Repair Generator 只能提交补丁，不能写入接受状态；接受必须来自独立 Evaluator。
5. 正式 Schema 只允许契约枚举，拒绝 `theore_misuse`、`algebraic_mismatch` 等非正式拼写。

结论：在以上执行约束和案例分歧得到书面裁决后，成员 B 同意将 M0 冻结为 `v0.1`。
