# M8 人工证据 15：外部代码、状态机、指标与泄漏审查

> [!IMPORTANT]
> 单元测试和内部交叉审查不能穷尽权限绕过、缓存碰撞、数据泄漏、指标漏计和发布配置风险；实现者也不能作为自己的独立外部 reviewer。

## 机器无法可靠验证

- 未覆盖路径是否允许角色伪造、Generator 自审、陈旧补丁重放或跨 proof 引用；
- 事务、版本、DAG、失效、缓存和拓扑重验组合是否存在语义漏洞；
- 指标实现是否选择性漏掉失败、零分母、超时或不适用样本；
- Gold、参考修复、测试答案或私有数据是否通过 Prompt、日志、缓存、fixture 或构建产物泄漏；
- 外部 reviewer 是否独立且覆盖关键攻击面；
- finding 的修复是否引入新问题并得到原 reviewer 复验。

## 需要人工检查

由未参与实现的外部代码审查者对发布候选的 Controller、Evaluator/Repair 边界、运行器、缓存、评分聚合、数据装载和发布脚本做源码与对抗审查。数学语义问题转交 Person A/数学专家，不由代码 reviewer 代签。

## 建议检查步骤与证据

1. 冻结审查 commit、依赖锁、配置和威胁模型，记录 reviewer 独立性与相关经验。
2. 沿“输入 → 模型调用 → 解析 → 裁决 → 证书 → 补丁 → review → apply → invalidate → recheck → aggregate”逐层追踪信任边界。
3. 对抗测试角色伪造、重复 ID、陈旧版本、未来/跨题边、循环、依赖重定向、删除拼接、部分回滚、乱序重验和缓存碰撞。
4. 从原始终态手算若干指标，覆盖成功、失败、超时、弃权、零分母、not applicable 和重试耗尽，并与聚合输出比较。
5. 搜查 Prompt、数据加载、日志、异常、缓存键、测试 fixture、构建包和 Git 历史中的 Gold/答案/个人信息泄漏路径。
6. 每个 finding 记录文件行、复现步骤、严重度、影响范围和建议；项目方修复后由同一外部 reviewer 复验。
7. 若严重 finding 影响历史结果，确定需重跑的配置、指标、论文数字和案例。

最低证据：冻结 commit、威胁模型、覆盖清单、对抗复现、逐项 findings、修复提交、复验结论、未覆盖范围和外部签署。

## 通过判据

- 高风险路径均被源码审查并有正反测试；不存在未解决的高严重度 finding。
- 指标手算与程序结果一致，失败与零分母口径符合冻结协议。
- 未发现 Gold/答案/敏感数据进入禁止上下文；发现项已清理且影响已重跑。
- 修复由外部 reviewer 复验，剩余限制明确记录。

## 不通过判据

- 只运行现有测试，没有独立读代码、构造攻击或手算指标。
- 内部作者或同一 Agent 的自审被标为外部代码审查。
- finding 只有“已修复”声明，没有复现、提交绑定和复验。
- 泄漏或指标错误可能影响结论，却未重跑相关实验和更新论文。

## 边界情况与常见误判

- 静态扫描未报警不等于无语义泄漏；例如 Gold 字段合法存在但进入了模型上下文。
- 100% 测试覆盖不代表状态组合和攻击面已覆盖。
- fixture 中故意包含答案可以接受，但必须证明正式运行路径完全隔离。
- 外部 reviewer 使用自动工具没有问题，但最终风险判断和签署仍是人工责任。
