# M6 人工证据 10：真实基线/消融运行完整性与混杂审计

> [!IMPORTANT]
> 当前 fixture 能证明账本规则，但不能证明真实 provider 调用发生、失败未被筛除、费用与日志真实，也不能排除消融结果由配置外因素造成。

## 机器无法可靠验证

- 运行是否来自声明的真实模型与版本，而非 fixture、缓存、人工补写或替代模型；
- provider 侧失败、限流、重试、账单和版本漂移是否完整进入账本；
- 某方法的高低表现是否由服务时段、截断、上下文长度、工具故障、缓存或并发差异导致；
- token 与价格字段是否对应真实计费口径；
- 失败样本和不利运行是否被选择性删除；
- 配置冻结后实际请求是否仍与冻结内容一致。

## 需要人工检查

Person B 和独立执行审计者将 Controller 账本与 provider 控制台/导出、原始请求响应、时间戳和账单逐项对照；Person A 只参与判断混杂是否破坏数学可比性，不替代执行核验。

## 建议检查步骤与证据

1. 在运行前记录账号/项目、provider、模型版本或 snapshot、价格表、区域、依赖环境和时钟来源。
2. 随机抽取并重点覆盖成功、超时、重试耗尽、预算终止、Schema/tool/API 失败，逐条比对 provider request ID 与本地 `run_id`。
3. 对所有配置重建 `配置 × 样本` 矩阵，确认每格有唯一终态且 attempt 连续；将缺失格列为失败，不补写成功。
4. 从未删减调用明细重算 token、调用、墙钟和成本，并与账单总额及缓存命中分开核对。
5. 检查各方法调度时段、并发、超时、截断、重试和工具可用率；必要时采用交错/随机运行顺序。
6. 对异常差异做受控复跑，只允许使用冻结配置；复跑与原运行同时保留并按预注册规则计分。
7. 形成混杂登记表：因素、受影响配置/样本、证据、严重度、处理以及是否使结论降级。

最低证据：provider 原始导出、request ID 对照表、完整终态矩阵、账单与价格 snapshot、成本复算、环境/调度记录、混杂登记和独立审计签名。

## 通过判据

- 每个配置与样本均有可追踪真实终态；失败、超时与重试没有从任何相关分母删除。
- 抽查请求与 provider 记录一致，真实成本可由冻结价格表和调用明细复算。
- 方法间运行条件一致或差异被量化；不存在足以替代目标机制解释主要结果的未控制混杂。
- 所有受控复跑依预注册规则计入，原始运行不可覆盖。

## 不通过判据

- fixture、人工构造输出或缓存结果被当作真实模型 Pilot。
- 无 provider 证据却声称精确模型版本、调用真实性或真实成本。
- 失败格缺失、成功重试覆盖首轮失败，或按事后规则挑选最好一次。
- 方法在不同预算/工具/截断条件下运行，却将差异单独归因于被消融组件。

## 边界情况与常见误判

- provider 不提供固定 snapshot 时，应记录时间窗和漂移限制，而不是声称位级复现。
- 本地 token 估算可作诊断，不能替代账单口径。
- 缓存命中不是模型调用；成本和延迟应分栏，但按协议决定是否纳入系统级指标。
- 临时服务故障可支持敏感性分析，不自动授权删除该轮。
