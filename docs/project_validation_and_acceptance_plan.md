# 项目验证与强制验收计划

版本：`v0.1-draft`  
适用范围：M0–M8  
项目：依赖图驱动的双 Agent 自然语言数学证明审计与局部修复 Harness

## 1. 文档目的与验证原则

### 1.1 文档目的

- 汇总项目从研究定义、数据标注、Evaluator、反例、Repair Generator、Controller 到论文发布所需的全部验证。
- 为 M0–M8 提供统一的阶段验收依据，避免只以“代码完成”或“模型能运行”作为完成标准。
- 明确数学判断、人工裁决、确定性程序检查、外部工具验证和实验统计之间的权限边界。
- 为每项核心结论保留可追踪证据，使结果能够复核、回放和复现。

### 1.2 验证角色

- **Person A：数学有效性负责人。** 负责证明语义、节点、依赖、局部义务、错误类型、定理适用性、反例范围、修复数学正确性和金标数学审查。
- **Person B：执行与实验负责人。** 负责 Schema、Controller、状态机、版本、缓存、Repair Generator、运行器、指标、实验配置和复现基础设施。
- **Controller：确定性执行程序。** 只负责格式、状态、图结构、版本、失效传播、调用轨迹和运行证据，不创造数学裁决。
- **第二标注者或第三方专家：独立复核者。** 用于双人精标、争议裁决、全局反例、高风险定理和论文代表案例复核。
- **外部工具：辅助核验者。** Python、SymPy、SAT/SMT、有限穷举或证明助手可以核验其能力范围内的事实，但工具结果必须与自然语言命题正确对齐。

### 1.3 通用验证原则

- Agent 不能以自己的输出验证自己的正确性；Repair Generator 不能接受自己的补丁。
- Schema 合法只说明结构合法，不说明数学正确。
- 检索到定理只说明存在候选，不说明定理适用或节点已闭合。
- 未找到反例不构成正确性证据；工具超时或返回 `unknown` 也不构成无反例证据。
- 节点修改后，所有依赖旧版本的直接和间接后代必须失效并重新验证。
- 数学裁决、错误类型、反例范围和 Controller 生命周期状态必须分字段保存。
- 所有核心验证均需留下版本化证据；口头确认不能作为阶段验收记录。

### 1.4 每项验证的标准记录

每项正式验证至少记录：

- `validation_id`：唯一编号。
- `target`：被验证对象及其版本。
- `owner`：主验证负责人。
- `reviewer`：独立复核人。
- `method`：人工、程序、外部工具或混合方法。
- `inputs`：使用的数据、上下文、配置和依赖版本。
- `result`：`pass`、`fail`、`needs_revision` 或 `undetermined`。
- `evidence`：测试、日志、差异、证书、引用或人工意见。
- `limitations`：本次验证没有覆盖的内容。
- `timestamp`：验证时间。

# 第一部分：全部验证目录

## 2. 研究定义与术语验证

### 2.1 研究目标验证

- 确认项目研究的是已有自然语言证明的审计和局部修复，而不是开放问题自主证明。
- 确认第一阶段领域边界、输入形式和输出证据强度均有明确说明。
- 确认每个研究问题都有对应数据、基线、指标和可证伪条件。
- 确认“双 Agent”不是单独贡献，核心贡献落在错误证书、依赖图、反例核验、局部补丁和后代重验证闭环。

### 2.2 术语可操作性验证

- 检查 `accepted`、`accepted_with_gap`、`unsupported`、`ambiguous` 和 `undetermined` 能否由不同人员稳定使用。
- 检查数学裁决、诊断错误、反例作用范围和生命周期状态是否彼此独立。
- 检查“直接依赖”“第一错误”“最小修复”“修复成功”等概念是否有可执行判据。
- 对边界案例进行双人独立判断，并书面裁决所有分歧。

### 2.3 非目标与表述验证

- 不将自然语言验证表述为形式化机器证明。
- 不把增加假设、削弱结论或改变定义域计为原问题修复成功。
- 不把未找到反例、检索相似度或模型置信度表述为数学证明。
- 不以整篇重写代替局部修复，除非实验明确把它作为独立基线。

## 3. 原题、来源与参考证明验证

### 3.1 原题完整性验证

- 检查定理、问题、量词、假设、定义域、值域、数学结构和符号是否完整。
- 检查 OCR、转录、编码或排版是否改变数学含义。
- 检查题设假设是否自相矛盾，结论是否与题目要求一致。
- 对有争议题目记录解释分支，不擅自选取有利于系统的解释。

### 3.2 原题真实性验证

- 对正确题目保存可信参考证明或权威来源。
- 对故意设置为错误的定理保存经过核验的全局反例。
- 对教材、论文或题库来源保存出处、版本、页码或稳定标识。
- 对外部来源进行许可和可发布性检查。

### 3.3 参考证明验证

- 逐步检查参考证明的每个推理是否成立。
- 检查是否存在隐藏假设、循环论证、目标偷换或定理误用。
- 检查正确结论是否搭配了错误证明，避免只看最终答案。
- 关键参考证明由 Person A 与独立复核者分别验证。

## 4. 节点表示验证

### 4.1 节点切分验证

- 检查节点是可独立判断数学角色的最小完整片段，而不是语法残片。
- 检查条件句、分类讨论、反证作用域和跨句引用没有被错误拆分。
- 检查复合断言是否需要拆分，拆分后是否保持原始逻辑。
- 比较双人节点边界标注，并报告 segmentation precision、recall 和 F1。

### 4.2 节点类型验证

- 检查 `definition`、`assumption`、`introduction`、`claim`、`calculation`、`conclusion` 和 `citation` 的使用一致。
- 对一个节点具有多个角色的情况记录主要类型和辅助证据字段。
- 检查节点类型是否会错误地绕过应有的数学验证。
- 对混淆矩阵中的高频混淆类型进行人工抽查。

### 4.3 源文本对齐验证

- 检查 `source_span` 与原文完全对应。
- 检查节点顺序、标点、公式和 Unicode 符号没有被意外修改。
- 检查合并或拆分节点后，所有 source span 无遗漏、重叠或越界。
- 对 OCR 输入保存原始图像或源文件定位，以便回查。

### 4.4 自包含命题验证

- 检查代词、编号引用、“由上式”“同理”等是否被正确消解。
- 检查量词、否定、条件前件、变量作用域和数学结构没有丢失。
- 检查改写后的命题与原节点逻辑等价，而不是更强或更弱。
- 对无法唯一消解的节点保留多个解释或标记 `ambiguous`。

## 5. Ambient context 与局部上下文验证

### 5.1 Ambient facts 来源验证

- 每条背景事实必须引用题面、显式假设、标准定义或已核验来源。
- 不允许从学生证明、后续节点或预期答案中提取背景事实。
- 不允许根据题目主题自动补充交换性、紧致性、连续性、非零性等条件。
- 无法确定的候选背景条件应进入 abstention 记录。

### 5.2 类型与作用域验证

- 检查变量属于实数、整数、群、域、向量空间等类型是否准确。
- 检查局部假设只在对应证明分支内生效。
- 检查反证假设、分类讨论条件和临时定义没有泄漏到其他分支。
- 检查前一显式子问题的已接受结论只传播到合法的后续子问题。

### 5.3 局部上下文隔离验证

- 当前节点只能使用全局假设、合法 ambient facts 和已接受的直接父节点。
- 不得使用后续节点、无关前序节点、被拒绝节点或 stale 节点。
- 检查上下文既没有漏掉必要信息，也没有通过加入过多信息弱化审计难度。
- 使用人工构造的上下文泄漏案例做回归测试。

## 6. 依赖图验证

### 6.1 图结构程序验证

- 检查节点 ID 唯一、边端点存在、无自环、无重复边和无未来边。
- 检查整体为 DAG，并能生成稳定拓扑序。
- 检查删除、替换或插入节点后没有悬空边。
- 检查子问题图和临时规则传播不形成跨题泄漏。

### 6.2 依赖语义人工验证

- 检查父节点是否真的是按原证明路线验证目标节点所必需的直接依赖。
- 区分直接依赖、间接依赖、主题相关和标准背景知识。
- 检查关键依赖遗漏和无关依赖加入。
- 对分叉、汇合、反证和分类讨论图进行专家复核。

### 6.3 图质量指标验证

- 报告 edge precision、recall 和 F1。
- 单独报告关键依赖遗漏率，避免高比例无关简单边掩盖严重漏边。
- 分图类型报告性能，如线性链、分叉、汇合和多层 DAG。
- 将图错误与后续验证错误分开归因。

## 7. 局部证明义务验证

### 7.1 义务构造验证

- 验证义务形式为“全局假设 + 已核验背景事实 + 已接受直接父节点 ⊢ 当前目标”。
- 检查目标与 self-contained claim 一致。
- 检查依赖上下文绑定正确节点版本和依赖指纹。
- 检查被阻塞节点不会产生伪造的可验证义务。

### 7.2 义务强弱验证

- 检查遗漏前提是否让义务变得过强。
- 检查加入无关或后续结论是否让义务变得过弱。
- 检查定义展开和标准背景知识的加入是否有明确规则。
- 对典型义务进行人工重建，与系统输出逐项比较。

## 8. 数学裁决验证

### 8.1 `accepted` 验证

- 必须存在明确适用的原子规则、定义或已核验原子计算。
- 所有规则适用条件必须在合法上下文中成立。
- 不得仅凭检索结果、语言流畅度或模型高置信度接受。
- 接受记录必须保存使用的证据和条件映射。

### 8.2 `accepted_with_gap` 验证

- 目标必须确实能从合法上下文推出。
- 必须存在至少一个新的、可独立真假判断的中间命题。
- 提供的桥接链必须逐步通过核验，且不能新增假设或循环使用目标。
- 不按句子长度、节点数量或模型主观难度区分 gap。

### 8.3 `unsupported`、`ambiguous` 与 `undetermined` 验证

- `unsupported` 要求目标解释和上下文已固定，但当前推理缺乏支持或规则不适用。
- `ambiguous` 要求至少两个合理解释会产生不同裁决，并保存解释分支。
- `undetermined` 表示证据不足或系统能力不足，不能被当作数学错误。
- 同时报告弃权率，防止系统通过大量 `undetermined` 虚假降低错误接受率。

### 8.4 第一错误位置验证

- 第一错误按原证明顺序确定。
- 表示错误、数学错误和下游阻塞分别记录。
- 无效父节点造成的后代阻塞不能重复计为新的第一错误。
- 多错误证明应保存全部错误，但主要指标使用预先定义的 first-error 规则。

## 9. 错误诊断与 Error Certificate 验证

### 9.1 错误类型验证

- 区分 `missing_assumption`、`theorem_misuse`、`algebraic_invalidity`、`target_mismatch` 和 `dependency_error`。
- 区分 `false_local_claim` 与 `false_theorem`。
- 区分 `segmentation_error`、`interpretation_ambiguity` 和数学证明缺口。
- 对同一证据阶段允许主错误类型与补充诊断并存，但 Schema 必须固定二者关系。

### 9.2 失败推理边验证

- 明确列出所使用的父节点或全局假设、目标节点和试图使用的规则。
- 失败边必须是最小可定位关系，不能只写“第 N 步有问题”。
- 缺失条件、非法操作、目标错配或反例必须与失败边直接相关。
- 对含多个可能失败点的节点保存候选与最终裁决依据。

### 9.3 Error Certificate 完整性验证

- 证书绑定精确的 `(proof_id, node_id, version)` 和依赖指纹。
- `local_context` 完整且不包含非法信息。
- `error_type`、`missing_condition` 和反例证据相互一致。
- `repair_constraints` 明确允许操作、禁止修改内容和最大步骤预算。

### 9.4 Error Certificate 可消费性验证

- Repair Generator 仅凭公开证书和允许上下文即可提出局部补丁。
- 证书不泄露 Evaluator 隐藏提示或不必要的完整推理过程。
- 对证书缺失字段、矛盾字段和过期版本进行负向测试。
- 比较结构化证书与自由文本批评的修复效果。

## 10. 定理检索与引用验证

### 10.1 定理库条目验证

- 检查定理陈述、前提、结论、方向、变量类型和适用领域。
- 保存可信来源、版本和可追踪标识。
- `deterministic_safe` 规则必须经过更严格的双人复核。
- 检查 OCR、抽取和规范化是否改变定理含义。

### 10.2 检索质量验证

- 建立必要规则、可选规则、不适用高相似规则和错误方向规则的检索金标。
- 报告 Recall@K、Precision@K、MRR 和必要定理遗漏率。
- 报告不适用规则高排名率和跨领域误检率。
- 对 query 改写、公式规范化和同义表述做稳定性测试。

### 10.3 定理适用性验证

- 将“检索到”与“条件满足”和“节点闭合”分成三个独立状态。
- 逐项映射定理前提到合法局部上下文。
- 检查使用方向、变量类型和结论形状。
- 若本地无法核验必要定理，才查询权威外部资料并保存来源。

## 11. 计算与外部工具验证

### 11.1 计算节点验证

- 核验整数、有理数、根式、绝对值、等式链和不等式变换。
- 检查除零、开方、平方、取对数和单调变换的前提条件。
- 检查表达式被完整解析，任何未支持片段均不得被静默忽略。
- 数值抽样不能替代一般恒等式证明。

### 11.2 工具输入对齐验证

- 检查程序编码的变量、类型、约束和目标与自然语言命题一致。
- 保存规范化表达式、工具版本、参数和完整输出。
- 对浮点结果进行精确化或误差界验证。
- 工具超时、解析失败或 `unknown` 应保持开放状态。

### 11.3 外部工具交叉验证

- 高风险结果尽可能由两种独立方式验证，如 SymPy 加人工代入。
- SAT/SMT 的不可满足结果要检查约束编码完整性。
- 有限穷举要说明搜索空间和完备范围。
- 证明助手结果要确认形式化陈述与原自然语言命题一致。

## 12. 反例验证

### 12.1 候选反例结构验证

- 指定目标节点、版本、数学结构、变量赋值和反例范围。
- 为每项全局假设、局部前提和目标否定提供独立检查项。
- 保存生成者、核验器、工具版本和执行轨迹。
- 格式合法的候选仍处于 `pending_verification`，不能直接成为证据。

### 12.2 前提满足验证

- 逐项验证全部全局假设、局部假设、类型条件和结构公理。
- 检查直接父节点命题在该实例中成立。
- 任一必要前提失败时拒绝候选反例。
- 不允许通过改变定义域、数学结构或解释来制造反例。

### 12.3 目标否定验证

- 检查候选确实让目标结论为假。
- 对蕴含命题要求前件真且后件假。
- 对存在、唯一、全称和等价命题采用对应的正确否定标准。
- 不允许用无关表达式不相等冒充目标被否定。

### 12.4 局部与全局范围验证

- 局部反例只否定当前节点，不自动否定原定理。
- 全局反例必须满足原题全部假设并直接否定最终结论。
- 全局反例要求程序核验和至少一次独立人工复核。
- 对局部错误但原定理可修复的案例保存替代路径说明。

### 12.5 无效反例与未发现反例验证

- 记录候选因遗漏假设、目标未被否定、结构改变或工具失败而无效的原因。
- 分别报告反例发现率和反例有效率。
- 未发现反例不能提升节点裁决。
- 反例搜索预算、超时和搜索范围必须进入实验记录。

## 13. 人工精标验证

### 13.1 标注员资格验证

- 记录数学背景、可覆盖领域和培训情况。
- 使用资格测试验证对关键标签边界的理解。
- 定期使用隐藏校准题检查标注漂移。
- 对超出标注员能力范围的题目允许弃权并转交专家。

### 13.2 双人独立标注验证

- 节点边界、类型、依赖、裁决、错误类型、反例和修复均尽量双人独立标注。
- 独立标注前不得查看对方答案或模型预测。
- 两份原始答案永久保留，不用最终裁决覆盖。
- Controller 自动生成差异，但不替人做数学裁决。

### 13.3 一致性与分歧验证

- 计算节点边界 F1、类型一致率、edge F1、verdict 一致率和 first-error 一致率。
- 分别统计概念歧义、证据不足、粗心错误和指南缺陷导致的分歧。
- 双方先分别写理由，再进行共同裁决。
- 无法达成一致时由第三专家裁决并记录依据。

### 13.4 金标变更验证

- 每次金标修改必须有原因、审批人和影响范围。
- 修改标签定义时必须创建新版本并提供迁移说明。
- 主实验开始后不得根据模型结果修改测试集金标，除非作为公开勘误并重跑全部方法。
- 金标版本必须进入 RunManifest。

## 14. Benchmark 数据质量验证

### 14.1 数据组成验证

- 同时包含正确证明、真实缺口、错误推理、局部假命题、错误定理和不确定样本。
- 同时包含人工注入错误、学生真实错误和模型自然错误。
- 覆盖多种证明长度、图结构、错误位置和难度。
- 第一阶段以代数为主，扩展领域前先验证标签可迁移性。

### 14.2 错误注入验证

- 注入前证明必须经过正确性验证。
- 确认只注入预定错误，没有意外制造第二错误。
- 注入后错误位置、类型和影响范围明确。
- 由未参与注入的人对修改前后版本进行差分复核。

### 14.3 去重与泄漏验证

- 检查完全重复、变量改名、数值替换、翻译重复和模板近重复。
- 同一原题的正确版与错误版不能跨训练、开发和测试集泄漏。
- 检查定理库、Prompt 示例、参考修复和模型上下文是否包含测试答案。
- 对相邻教材题和同源证明进行分组划分。

### 14.4 分布与代表性验证

- 报告领域、来源、证明长度、节点数、图深度、错误类型和错误位置分布。
- 检查是否过度集中于明显除零、单步计算或人工模板错误。
- 检查正确/错误、单错误/多错误和可自动核验/需专家核验的比例。
- 对数据偏差及其对论文外推性的影响进行书面说明。

### 14.5 数据许可与隐私验证

- 检查教材、题库、论文和第三方数据的使用许可。
- 对学生答案移除姓名、学校、学号和评分信息。
- 记录模型生成数据、人工改写数据和真实数据的来源比例。
- 发布前完成数据卡、许可证和隐私复核。

## 15. Evaluator Agent 验证

### 15.1 分阶段调用验证

- 切分、分类、ambient、建图、义务、裁决和诊断分别使用明确契约。
- 上一阶段未通过 Schema 或语义验证时，不允许静默进入下一阶段。
- 各模块可在使用上游金标的条件下独立评测。
- 保存每次模型调用的输入、输出、Prompt 版本和模型配置。

### 15.2 输出一致性验证

- 裁决、理由、错误类型、失败边和反例证据不能相互矛盾。
- 输出引用的节点、规则和证书必须存在。
- 对模糊、空泛或未定位具体推理边的诊断进行拒绝测试。
- 对同一输入多次采样，分析裁决稳定性和相关失败。

### 15.3 信息边界验证

- Evaluator 不得使用后续节点和测试集金标作为证据。
- 补丁复核时只读取公开 Patch 和合法上下文，不读取 Repair Generator 隐藏推理。
- 在 grading 模式下不得静默修改证明。
- 对提示注入、伪造 JSON 和证明文本内控制指令进行防护测试。

## 16. Repair Generator 验证

### 16.1 输入隔离验证

- 仅提供原题、失败节点、直接依赖、Error Certificate、允许规则和修改预算。
- 不提供 Evaluator 隐藏提示、完整金标修复或无关证明分支。
- 保存实际输入快照，以便审计信息泄漏。
- 对缺少必要证书字段的输入要求拒绝或返回无法修复。

### 16.2 Patch 结构验证

- 操作类型仅限契约允许的 `insert_before`、`replace`、`delete` 或 `mark_irreparable`。
- Patch 绑定目标精确版本，并列出使用的依赖和规则。
- 不得引用未来节点、过期节点或未提供的隐藏上下文。
- 不得超过节点数、步骤数或修改范围预算。

### 16.3 Patch 数学验证

- 新增和替换节点必须逐个通过 Evaluator 独立检查。
- 补丁必须解决原 Error Certificate 中的失败边。
- 不得隐藏新增假设、改变定义域、削弱结论或只做措辞掩盖。
- 对声称不可修复的案例也要抽样检查是否存在明显局部修复。

### 16.4 修复最小性验证

- 检查补丁只修改错误节点及必要邻近节点。
- 逐一删除新增或替换步骤，确认删除后是否导致复核失败。
- 最小性只相对于实际考虑和接受的候选补丁，不声称全局最短证明。
- 同时报告补丁节点数、文本改动量和无关分支修改量。

### 16.5 新错误引入验证

- 检查补丁自身是否包含新错误。
- 检查后代是否因新版本产生新的不成立推理。
- 分别报告修复成功率和新错误引入率。
- 对“修复目标节点但破坏最终证明”的情况计为失败。

## 17. 双 Agent 独立性与共同盲点验证

### 17.1 裁决权分离验证

- Repair Generator 只能提交补丁，不能写入接受状态。
- Evaluator 必须在独立调用中复核补丁。
- Controller 只有在收到合法 PatchReview 后才能应用接受状态。
- 对绕过复核的非法状态转换编写测试。

### 17.2 信息隔离验证

- Evaluator 和 Repair Generator 不共享隐藏推理过程。
- Repair Generator 不获得完整裁决 Prompt。
- Evaluator 复核时重新构造义务，而不是复制首次判断。
- 日志证明实际发送的信息符合隔离设计。

### 17.3 共同盲点压力测试

- 测试两个 Agent 同时引用虚构定理、遗漏同一条件或接受同一错误补丁。
- 比较同模型双角色、独立采样和异模型双角色。
- 高风险节点增加程序核验或第二 Evaluator 复核。
- 冲突无法解决时保留 `undetermined`，不以语言说服力或简单多数决替代证据。

## 18. Controller 与 Schema 验证

### 18.1 Schema 验证

- 检查必填字段、类型、枚举、ID、版本、数值范围和 null 语义。
- 对缺字段、额外字段、非法枚举和非正式拼写编写负向 fixture。
- Schema 变更必须提供迁移说明和向后兼容测试。
- Schema 通过不能自动生成数学接受状态。

### 18.2 状态机验证

- 覆盖 pending、evaluated、failed、patch_pending、patch_submitted、rechecking、accepted、rejected、stale 和 terminated 等状态。
- 对每个合法转换编写正向测试，对越级接受、缺少复核和过期写入编写负向测试。
- 数学裁决和生命周期状态分别保存。
- 状态转换事件必须写入不可覆盖的审计日志。

### 18.3 节点版本验证

- `(proof_id, node_id, version)` 唯一且可追溯。
- 新版本保留来源关系，旧版本和旧裁决不被覆盖。
- 过期版本 Patch 必须被拒绝。
- 并发补丁冲突、回滚和重新提交均有确定性行为。

### 18.4 后代失效验证

- 修改节点后，全部直接和间接后代旧裁决变为 stale。
- 无关分支不应失效。
- 受影响节点按拓扑顺序重新验证。
- 使用链、分叉、汇合、多层 DAG 和独立分支进行测试。

### 18.5 缓存验证

- 缓存指纹包含代码、定理库、题目上下文、节点、图、父节点结果、Prompt、模型和工具配置。
- 任一依赖组件变化时，相关节点及后代缓存必须失效。
- 损坏或旧格式缓存必须被忽略，不得作为数学证据。
- 测试缓存命中不会改变无缓存运行的最终结果。

### 18.6 Session 与恢复验证

- 验证首轮 pending、部分响应恢复、多轮 ledger、异常退出和幂等重放。
- 验证输入或配置变化会被检测。
- 已完成且指纹相同的节点不重复调用，stale 节点必须重新入队。
- 完成条件要求零待处理义务，或明确记录无进展终止。

### 18.7 重试、终止与回滚验证

- 限制模型重试次数和修复轮数。
- 检测等价错误、等价补丁和无进展循环。
- 全局反例、必须改变题目和长期冲突触发对应停止策略。
- 回滚后图、版本、缓存和当前状态保持一致。

### 18.8 并发与依赖前沿验证

- 只允许依赖前沿中的独立节点并行。
- 父节点未解决时，后代不得提前获得有效裁决。
- 父节点失败后，相关并发后代结果应被取消或废弃。
- 并发结果合并必须确定，不能因完成顺序改变数学状态。

## 19. 软件质量与安全失败验证

### 19.1 自动化测试验证

- 核心模块具备单元测试、契约测试、回归测试和端到端测试。
- 对边界输入、异常输入、Unicode、OCR 和超长输入进行测试。
- 对图、缓存、状态机和指标实现增加属性测试或参数化测试。
- 每个已修复缺陷至少增加一个回归案例。

### 19.2 安全失败验证

- JSON 不完整、图不合法、定理来源不明和反例无法核验时应拒绝证据或保持 `undetermined`。
- 表达式部分解析成功时不得只验证已支持片段。
- API 超时、工具错误和 session 损坏不得被转化为数学错误。
- 多个确定性规则冲突时不得任意选择一个关闭节点。

### 19.3 提示注入与不可信输入验证

- 将证明文本内的指令、伪造系统提示和伪造 JSON 视为待审计数据。
- 不允许输入文本改变工具权限或系统工作流。
- 对伪造定理引用、要求泄露隐藏提示和诱导直接接受进行测试。
- 日志和用户数据中的敏感信息不得进入公开输出。

### 19.4 性能与压力验证

- 测试长证明、深依赖链、宽 DAG、多错误、多轮修复和大定理库。
- 记录时间、内存、调用数、token、延迟和缓存收益。
- 验证大规模失效传播不会漏掉后代或错误影响无关分支。
- 为超出预算的运行提供可解释的终止状态。

## 20. 实验设计验证

### 20.1 基线公平性验证

- 各方法使用相同数据划分、评价标准和失败处理规则。
- 模型、token 预算、工具权限和最大轮数尽量可比，差异必须公开。
- 不给完整系统独有的金标信息。
- 不因基线实现较弱而夸大完整系统收益。

### 20.2 消融纯度验证

- 每项消融只移除目标组件，其他输入、预算和流程尽量保持不变。
- 无图、无反例、无错误证书、无撤销和单轮修复分别实现。
- 自由文本反馈与结构化证书的信息量差异需要说明。
- 保存每个消融的完整配置，而不是只保存显示名称。

### 20.3 实验预冻结验证

- 主实验前冻结研究问题、数据版本、指标、Prompt、模型配置和停止规则。
- 冻结内容生成 hash 并写入 RunManifest。
- 查看测试结果后不得静默修改评价口径。
- 必要勘误需记录、重跑全部受影响方法并公开影响。

## 21. 指标与统计验证

### 21.1 指标定义验证

- 每个指标具有明确分子、分母、聚合单位和 abstention 处理规则。
- 区分 node-level、proof-level 和 first-error 指标。
- 使用小型手算 fixture 验证指标代码。
- 多错误证明、失败运行和缺失输出的计分方式预先确定。

### 21.2 安全指标验证

- 错误接受率作为首要安全指标之一。
- 同时报告弃权率和覆盖率，防止全部拒绝策略获得表面安全。
- 分别报告错误证明中的接受率，以及被系统接受结果中的错误比例。
- 按错误类型、难度和证明长度分层报告。

### 21.3 反例与修复指标验证

- 分别报告反例发现率、有效率和假反例率。
- 分别报告修复成功率、最小性和新错误引入率。
- 后代重验证正确率必须单独报告。
- 修复成功要求最终目标路径无 invalid、stale、blocked 或 unresolved 节点。

### 21.4 统计可靠性验证

- 使用配对比较和 bootstrap 置信区间。
- 报告多 seed、多采样或多模型组合的方差。
- 多重比较时使用适当修正并报告效应量。
- 不只报告最佳单次运行。

## 22. 运行、成本与复现验证

### 22.1 RunManifest 验证

- 保存数据、代码、定理库、Schema、Prompt、模型和工具版本。
- 保存温度、seed、token 预算、重试、停止规则和并发设置。
- 保存每个样本的完成、失败、超时和终止状态。
- Manifest 与实际输出文件相互校验。

### 22.2 失败运行验证

- API 超时、Schema 失败、工具失败、无进展和预算耗尽均不得删除。
- 失败运行如何计入指标必须预先规定。
- 重试后的原始失败仍保留。
- 报告不同方法的失败率和失败原因分布。

### 22.3 成本验证

- 记录每题和每节点调用次数、token、延迟、工具调用和修复轮数。
- 比较完整系统相对基线的增量成本和增量收益。
- 统计失败调用和重试成本。
- 对同模型双角色和异模型组合分别报告。

### 22.4 端到端回放验证

- 从输入重放节点、图、义务、检索、裁决、诊断、修复、失效和最终结果。
- 任一最终裁决都能追溯到节点版本、依赖指纹、模型调用和人工裁决。
- 在独立目录或独立机器进行小规模复现。
- 无外部模型时仍能运行确定性测试和 fixture 回放。

## 23. 鲁棒性与对抗验证

### 23.1 表达鲁棒性验证

- 测试中英文、LaTeX、Unicode、OCR、非标准符号和多级编号。
- 测试同义改写、变量改名、合法步骤重排和无关文本加入。
- 检查裁决是否依赖表面措辞而非数学结构。
- 对明显语义变化和仅表述变化分别建立对照样本。

### 23.2 数学对抗案例验证

- 覆盖隐藏除零、量词交换、逆命题、局部变量逃逸和定义域偷换。
- 覆盖循环论证、目标漂移、虚构定理、定理条件缺失和数值例子代替一般证明。
- 覆盖正确结论搭配错误证明、错误中间节点搭配正确最终结论。
- 覆盖多个独立错误和上游错误污染大量后代。

### 23.3 模型与 Prompt 稳定性验证

- 比较不同 seed、temperature、模型版本和轻微 Prompt 改写。
- 分析同一输入多次运行的裁决一致性。
- 模型升级后使用固定回归集重新评估。
- Prompt 修改需报告性能、安全性、弃权率和成本变化。

## 24. 外部人工与独立验证

### 24.1 第三方数学专家验证

- 复核全部全局反例和论文代表案例。
- 裁决 Person A 与 Person B 无法解决的数学分歧。
- 抽查每类错误、每类修复和高风险定理引用。
- 对异常高性能、异常低性能和反直觉结果进行独立审查。

### 24.2 外部代码审查

- 重点审查状态机、后代失效、缓存、指标和数据划分。
- 检查 stale 结果泄漏、测试集泄漏、错误分母和选择性排除失败运行。
- 审查 Controller 是否越权创造数学裁决。
- 对发布前版本保留审查意见和修复记录。

### 24.3 外部复现验证

- 在无作者本地状态的环境中安装和运行。
- 验证路径、依赖、配置和复现命令完整。
- 小规模复现主要表格趋势或确定性结果。
- 记录无法完全复现的原因，如外部模型版本漂移。

## 25. 论文与发布验证

### 25.1 主张—证据对应验证

- 每项核心主张绑定具体实验、指标、数据和限制。
- 没有量化支持的内容只能表述为设计动机或定性发现。
- 不把相关性结果写成因果结论。
- 不将代数范围结果无条件外推到全部数学领域。

### 25.2 数字与图表一致性验证

- 论文表格、图表和摘要数字由原始结果自动生成或交叉核对。
- 分母、百分比、置信区间和样本量一致。
- 最佳结果不能来自未说明的 seed 选择。
- 失败运行、弃权和成本不得从图表中隐藏。

### 25.3 案例展示验证

- 每个案例包含必要原题、节点、依赖、错误、证据、修复和重验结果。
- 展示成功、错误接受、无效反例、错误修复、共同盲点和过度弃权案例。
- 案例由数学专家确认且与真实运行轨迹一致。
- 对编辑过的展示文本明确说明，不伪装成原始模型输出。

### 25.4 限制声明验证

- 明确自然语言审计不等价于形式证明。
- 明确反例搜索和定理库不完备。
- 明确双 Agent 可能存在相关失败。
- 明确数据、领域、模型版本、人工标注和复现限制。

### 25.5 发布完整性验证

- 发布代码、Schema、Prompt、数据卡、标注指南、系统卡和复现命令。
- 提供版本、许可证、隐私说明和已知限制。
- 确保公开文件不包含密钥、个人信息或受限数据。
- 发布包通过外部复现和最终清单检查。

# 第二部分：M0–M8 阶段验证计划

## 26. M0：研究范围与术语契约

### 26.1 必做验证

- 验证项目目标、非目标、领域范围和证据强度。
- 验证所有核心术语可由两人独立、稳定地使用。
- 验证数学裁决、错误类型、反例范围和生命周期状态分离。
- 使用至少 10 个边界案例验证 gap/invalid、local/global 和 blocked/error 的区别。

### 26.2 人工验证

- Person A 和 Person B 独立标注相同案例。
- 双方分别提交理由后再比较结果。
- 所有分歧形成书面裁决，原始答案永久保留。
- 无法解决的数学分歧交第三专家。

### 26.3 Controller 或程序验证

- M0 只验证 Controller 权限边界，不要求完整实现。
- 建立术语枚举原型，检查是否存在重叠或不可表达状态。
- 检查研究问题与核心指标是否一一对应。
- 冻结 M0 版本和后续变更规则。

### 26.4 退出标准

- 双人能够依据同一规范标注验收案例。
- 所有核心分歧已裁决。
- M0 文档标记为 frozen。
- 后续变更只能通过新版本和迁移说明完成。

## 27. M1：Schema 与 Controller 骨架

### 27.1 必做验证

- 验证 Proof、Node、Edge、Evaluation、ErrorCertificate、Counterexample、Patch 和 RunManifest Schema。
- 验证图结构、状态机、节点版本和补丁版本。
- 验证数学字段与执行字段分离。
- 验证至少两个无 LLM 修复会话可完整回放。

### 27.2 人工验证

- Person A 审查数学对象能否完整表达合法上下文、失败边和反例。
- Person B 审查状态转换、版本、回滚和运行记录能否执行。
- 双方交叉检查 Controller 没有越权做数学判断。
- 共享 Schema 必须双人批准。

### 27.3 Controller 或程序验证

- 正反 Schema fixture。
- DAG、自环、重复边、未来边和悬空引用测试。
- 缺失版本、过期 Patch、非法转换和缺少复核测试。
- Schema 迁移、序列化、Unicode 和回放测试。

### 27.4 退出标准

- 所有 fixture 通过预期结果。
- 非法图、无效反例和过期 Patch 均被拒绝。
- Controller 不能直接写入数学接受状态。
- Schema v0.1 与 Controller 状态表冻结。

## 28. M2：Pilot Benchmark

### 28.1 必做验证

- 验证原题、参考证明、错误注入、节点、依赖、裁决、反例和修复金标。
- 验证数据去重、来源、许可、分布和划分泄漏。
- 验证标注指南和标注员资格。
- 验证至少 50 个代数样本的双人精标流程。

### 28.2 人工验证

- Person A 和 Person B 独立标注，不查看模型输出。
- 每个全局反例由第二人独立核验。
- 错误注入样本由非注入者进行前后差分审查。
- 争议样本由共同裁决或第三专家裁决。

### 28.3 Controller 或程序验证

- 样本 ID、source span、节点覆盖、edge 和 DAG 校验。
- 自动生成两份标注差异和一致性统计。
- 近重复、变量改名和模板泄漏初筛。
- 数据版本、划分和金标 hash 固化。

### 28.4 退出标准

- 每个样本均有完整金标和审查记录。
- 所有分歧已分类并裁决。
- benchmark v0.1 冻结。
- 任何测试答案未泄漏到 Prompt、定理库或开发集。

## 29. M3：Evaluator v1

### 29.1 必做验证

- 分别验证切分、分类、ambient、self-contained claim、建图、义务、裁决和诊断。
- 验证局部上下文隔离和第一错误定位。
- 验证定理检索与适用性检查分离。
- 验证 Error Certificate 的完整性和可消费性。

### 29.2 人工验证

- Person A 使用金标上游输入分别审查各模块。
- 对 accepted、gap、unsupported、ambiguous 和 undetermined 抽样复核。
- 对错误接受案例做逐项数学错误分析。
- 对模型生成的 self-contained claim 和依赖边重点抽查。

### 29.3 Controller 或程序验证

- 每阶段 Schema 校验和失败阻断。
- Prompt、模型、响应和成本记录。
- graph、ambient、node response 和 session 缓存指纹验证。
- API 失败、空泛诊断、矛盾输出和格式错误回归测试。

### 29.4 指标验证

- Segmentation F1。
- Node classification macro-F1。
- Edge precision、recall、F1 和关键依赖遗漏率。
- First-error accuracy、verdict macro-F1、false acceptance rate 和 abstention rate。

### 29.5 退出标准

- 各模块能使用上游金标独立评测。
- 切分、图和数学验证错误可以分开归因。
- 所有接受节点具有明确证据。
- 所有非闭合节点具有合法诊断或保持 `undetermined`。

## 30. M4：反例模块

### 30.1 必做验证

- 验证候选反例、前提满足、目标否定和作用范围。
- 验证程序编码与自然语言命题对齐。
- 验证无效反例拒绝和未发现反例的保守处理。
- 验证 local counterexample 与 global counterexample 的不同系统动作。

### 30.2 人工验证

- Person A 复核数学结构、全部前提和目标否定。
- 全局反例由第二人或第三专家复核。
- 对程序无法覆盖的反例进行人工证明或保持未确定。
- 检查局部反例是否被错误升级为原定理反例。

### 30.3 Controller 或程序验证

- 候选反例始终先进入 pending 状态。
- 调用 Python、SymPy、SAT/SMT 或有限穷举并保存工具轨迹。
- 工具失败、超时、浮点不确定和部分解析均不得通过。
- 证书绑定精确节点版本，global 证书触发停止策略。

### 30.4 指标验证

- 反例发现率。
- 反例有效率。
- 假反例率。
- 全部前提满足率和 local/global 范围准确率。

### 30.5 退出标准

- 每份被接受反例均有完整证书。
- 全局反例均通过程序和人工双重验证。
- 无效候选不改变最终数学裁决。
- 未找到反例不增加接受置信度。

## 31. M5：Repair Generator 与闭环

### 31.1 必做验证

- 验证 ErrorCertificate 到 PatchProposal 的接口。
- 验证输入隔离、修改预算、版本绑定和操作范围。
- 验证补丁数学正确性、最小性和新错误引入。
- 验证后代撤销、拓扑重验、重试、终止和回滚。

### 31.2 人工验证

- Person A 独立复核所有 pilot 补丁的数学有效性。
- 检查是否增加假设、改变定义域、削弱结论或重写无关分支。
- 对最小性执行逐步删除检查。
- 对 `mark_irreparable` 抽样确认没有明显允许范围内的修复。

### 31.3 Controller 或程序验证

- Patch Schema、目标版本、未来引用、DAG 和预算检查。
- Patch 未经独立 PatchReview 不得应用为成功修复。
- 修改节点后计算完整后代闭包并标记 stale。
- 验证旧缓存失效、拓扑重验、等价补丁循环检测和回滚一致性。

### 31.4 端到端验证

- 使用正确可修复、不可修复、局部假命题、错误定理和多分支案例。
- 完整回放 diagnosis、certificate、patch、review、apply、invalidate 和 recheck。
- 检查最终目标路径没有 invalid、stale、blocked 或 unresolved 节点。
- 比较局部补丁与整篇重写基线。

### 31.5 指标验证

- Repair success rate。
- Patch minimality。
- New-error introduction rate。
- Descendant revalidation correctness。
- 平均修复轮数、调用数、token、成本和延迟。

### 31.6 退出标准

- Repair Generator 不能审核自己的补丁。
- 所有成功补丁通过独立 Evaluator 复核。
- 修改节点后没有旧后代结果泄漏。
- 改变题目的方案不计为原问题修复成功。

## 32. M6：基线与消融

### 32.1 必做验证

- 验证整篇直接判断、自我反思、普通 Generator–Critic 和完整系统的实现。
- 验证无图、无反例、无结构化证书、无撤销和单轮修复消融。
- 验证同模型双角色和异模型双角色。
- 验证各方法预算、工具权限和评价标准的公平性。

### 32.2 人工验证

- Person A 在运行前冻结数学可比性规则和核心指标。
- 抽查各基线实际收到的信息，确认没有不公平泄漏。
- 对各方法的错误接受和错误修复做盲态数学审查。
- 检查消融结果是否可以由配置外因素解释。

### 32.3 Controller 或程序验证

- 冻结数据、代码、Prompt、模型、预算和指标 hash。
- 保存全部成功、失败、重试和超时运行。
- 检查每种方法覆盖相同样本集合。
- 防止缓存跨方法或跨配置污染。

### 32.4 退出标准

- 所有基线和关键消融均可重复运行。
- 实验配置在查看测试结果前冻结。
- 失败运行有统一计分规则。
- 完整系统收益不能仅由更多调用或更大 token 预算解释。

## 33. M7：主实验

### 33.1 必做验证

- 验证 200–500 个高质量样本的数据和金标冻结。
- 验证多 seed、多采样和多模型组合。
- 验证核心指标、置信区间、成本和失败率。
- 验证主实验可以从 RunManifest 回放。

### 33.2 人工验证

- Person A 在尽可能不知道模型结果的情况下完成最终金标审计。
- 第三专家复核全局反例、争议案例和论文候选案例。
- 对异常结果、意外高分和主要失败类别进行独立错误分析。
- 检查定性结论是否有足够代表性案例支持。

### 33.3 Controller 或程序验证

- 确保全部样本均被运行或有明确失败状态。
- 自动检查 Manifest、结果文件和聚合表一致。
- 使用配对 bootstrap 生成置信区间。
- 在独立目录执行抽样复现和确定性回放。

### 33.4 退出标准

- 核心指标具有置信区间和效应量。
- 失败运行没有被删除。
- 数据、代码、Prompt、模型和指标版本完整可追踪。
- 主要结论在合理随机扰动下保持稳定，或明确报告不稳定性。

## 34. M8：论文与发布

### 34.1 必做验证

- 验证每项论文主张对应具体实验、指标和限制。
- 验证论文数字、图表和案例与原始结果一致。
- 验证代码、数据、Schema、Prompt、标注指南和复现命令完整。
- 验证许可证、隐私、系统卡和限制声明。

### 34.2 人工验证

- Person A 审核全部数学表述、反例、修复和能力边界。
- Person B 审核系统描述、实验配置、统计和复现说明。
- 第三专家复核论文代表案例和核心数学主张。
- 外部代码审查者检查状态机、缓存、指标和数据泄漏。

### 34.3 Controller 或程序验证

- 从原始结果重新生成论文表格和图表。
- 检查样本量、分母、百分比、置信区间和成本一致。
- 生成发布清单、文件 hash 和版本索引。
- 在干净环境执行最终复现命令。

### 34.4 退出标准

- 每项核心主张均有量化证据或明确标记为定性发现。
- 论文没有将自然语言审计夸大为形式证明。
- 发布包通过外部复现或记录明确的外部模型限制。
- 无密钥、个人信息、未授权数据或无法追踪的结果文件。

# 第三部分：建议设置的强制验收门

## 35. 数学证据强制门

### 35.1 人工金标门

- 核心测试集必须至少双人独立标注或一人标注加一人逐项复核。
- 原始标注、分歧和最终裁决均必须保留。
- 全局反例、争议修复和论文案例必须有第二位数学复核者。
- 未完成数学审查的数据不得进入主实验测试集。

### 35.2 反例证书门

- 所有接受的反例必须逐项满足前提并否定目标。
- 全局反例必须程序核验加人工核验。
- 无效候选和工具 `unknown` 不得改变数学裁决。
- 未找到反例不得被用作接受证据。

### 35.3 定理适用性门

- 定理检索结果不得直接关闭节点。
- 所有使用的定理必须核验陈述、来源、方向和适用条件。
- 无法确认的必要定理必须保持 `undetermined` 或进入外部核验。
- `deterministic_safe` 规则必须双人审核并有精确适用处理器。

## 36. 双 Agent 强制门

### 36.1 独立复核门

- Repair Generator 不得接受自己的补丁。
- 补丁必须由 Evaluator 在独立调用中重新构造义务并复核。
- 没有合法 PatchReview 的补丁不得进入成功状态。
- 高风险补丁必须增加程序核验、第二采样或异模型复核。

### 36.2 信息隔离门

- Repair Generator 不得接触测试金标、Evaluator 隐藏提示和无关证明分支。
- Evaluator 不得将 Repair Generator 隐藏推理作为数学证据。
- 每次调用保存输入快照，以证明信息边界实际执行。
- 发现信息泄漏时，受影响实验全部作废并重跑。

## 37. Controller 强制门

### 37.1 权限边界门

- Controller 不能创造数学裁决。
- Schema 通过、缓存命中或模型一致不能自动转为 `accepted`。
- 数学裁决和生命周期状态必须分字段保存。
- 所有状态转换必须有可追踪事件记录。

### 37.2 版本与失效门

- 每份裁决、证书和 Patch 必须绑定精确节点版本。
- 修改节点后，全部受影响后代必须 stale 并按拓扑序重验。
- 任一依赖指纹变化后不得复用旧缓存。
- 后代重验证未完成时不得宣告整题修复成功。

### 37.3 安全失败门

- 格式错误、图不合法、部分解析、工具失败和 API 超时必须 fail closed。
- 系统能力不足不能伪装成数学错误。
- 多轮无进展必须终止为 `undetermined` 或明确失败，而非强制给结论。
- 损坏的 session、缓存或运行记录不得作为证据。

## 38. 修复强制门

### 38.1 原问题保持门

- 增加假设、削弱结论、改变定义域或数学结构不计为原问题修复成功。
- Patch 只能修改 Error Certificate 允许的局部范围。
- 无关证明分支不得被重写。
- 任何问题变更建议必须单独标记和统计。

### 38.2 修复成功门

- 所有新增和替换节点均通过独立验证。
- 原失败边已被解决。
- 所有受影响后代已重新验证。
- 最终目标路径没有 invalid、stale、blocked 或 unresolved 节点。

### 38.3 新错误与最小性门

- 修复后必须检查新错误引入。
- 对声明为最小的补丁执行删除步骤复核。
- 修复成功率必须与新错误引入率同时报告。
- 只修好局部但破坏最终证明的补丁计为失败。

## 39. 数据与实验强制门

### 39.1 数据冻结门

- 主实验前冻结测试集、金标、划分和数据 hash。
- 测试集不得用于 Prompt 调参或规则开发。
- 近重复、同源改写和正确/错误配对不得跨划分泄漏。
- 金标勘误必须公开记录并重跑全部受影响方法。

### 39.2 实验预注册门

- 主实验前冻结研究问题、主要指标、基线、消融、预算和失败处理。
- 查看结果后不得静默改变分母、样本排除或成功标准。
- 所有方法使用可比较配置，差异必须披露。
- 完整系统收益必须与额外调用、token 和工具成本一起解释。

### 39.3 失败运行门

- 超时、工具错误、Schema 失败、无进展和预算耗尽均必须保留。
- 失败运行的计分规则必须预先定义。
- 不得选择性删除降低结果的 seed、样本或模型组合。
- 所有重试和失败成本计入总成本。

### 39.4 指标与统计门

- 错误接受率必须与弃权率、覆盖率同时报告。
- 反例发现率与有效率分开报告。
- 修复成功率与新错误引入率分开报告。
- 主指标必须有经过测试的实现和置信区间。

## 40. 发布强制门

### 40.1 主张一致性门

- 每项核心论文主张必须对应预先规定的实验和指标。
- 无量化支持的内容只能标记为定性观察。
- 不得把代数结果无条件外推到所有数学领域。
- 不得把自然语言模型接受表述为形式可靠性保证。

### 40.2 复现门

- 每个主实验具有完整 RunManifest。
- 论文数字能够从发布的原始结果重新生成。
- 确定性测试在干净环境全部通过。
- 外部模型无法完全复现时，必须说明版本漂移和允许误差。

### 40.3 外部审查门

- 至少一次外部数学案例抽查。
- 至少一次外部代码或实验审查。
- 至少一次独立环境的小规模复现。
- 外部发现的严重问题必须修复或在限制中明确披露。

### 40.4 合规门

- 发布数据具有明确来源、许可和数据卡。
- 学生或个人数据完成匿名化。
- 发布包不包含密钥、个人信息或受限内容。
- 代码、模型、定理库和第三方依赖许可证完成审查。

## 42. 验证完成定义

一项验证只有同时满足以下条件才算完成：

- 验证对象及版本明确。
- 验证方法和通过标准在查看结果前确定。
- 自动检查具有测试，人工判断具有复核人。
- 结果、失败和限制均被记录。
- 证据可以从项目索引定位并独立复查。
- 任何修订都触发受影响验证的重新执行。
